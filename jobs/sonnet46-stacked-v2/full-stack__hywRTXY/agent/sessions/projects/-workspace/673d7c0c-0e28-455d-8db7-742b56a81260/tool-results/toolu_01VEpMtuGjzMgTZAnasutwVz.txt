     1→# Attractor Specification
     2→
     3→A DOT-based pipeline runner that uses directed graphs (defined in Graphviz DOT syntax) to orchestrate multi-stage AI workflows. Each node in the graph is an AI task (LLM call, human review, conditional branch, parallel fan-out, etc.) and edges define the flow between them.

    23→## 1. Overview and Goals
    24→
    25→### 1.1 Problem Statement
    26→
    27→AI-powered software workflows -- code generation, code review, testing, deployment planning -- often require multiple LLM calls chained together with conditional logic, human approvals, and parallel execution. Without a structured orchestration layer, developers either write fragile imperative scripts or build ad-hoc state machines that are difficult to visualize, version, or debug.
    28→
    29→Attractor solves this by letting pipeline authors define multi-stage AI workflows as directed graphs using Graphviz DOT syntax. The graph is the workflow: nodes are tasks, edges are transitions, and attributes configure behavior. The result is a declarative, visual, version-controllable pipeline definition that an execution engine can traverse deterministically.
    30→
    31→### 1.2 Why DOT Syntax
    32→
    33→DOT is chosen as the pipeline definition format for several reasons:
    34→
    35→- **DOT is inherently a graph description language.** Workflow pipelines are directed graphs. Using DOT means the structure (nodes and edges) maps directly to the language's primary construct, rather than being encoded in a data format like YAML or JSON that has no native concept of graphs.
    36→- **Existing tooling.** DOT files can be rendered to SVG/PNG with standard Graphviz tooling, giving pipeline authors immediate visual feedback. Editors, linters, and parsers already exist.
    37→- **Declarative and human-readable.** A `.dot` file is a complete, self-contained workflow definition that can be version-controlled, diffed, and reviewed in pull requests.
    38→- **Constrained extensibility.** By restricting to a well-defined DOT subset (directed graphs only, typed attributes, no HTML labels), the DSL remains predictable while being extensible through custom attributes.
    39→
    40→For reference on DOT syntax, see the Graphviz DOT language specification: https://graphviz.org/doc/info/lang.html
    41→
    42→### 1.3 Design Principles
    43→
    44→**Declarative pipelines.** The `.dot` file declares what the workflow looks like and what each stage should do. The execution engine decides how and when to run each stage. Pipeline authors do not write control flow; they declare graph structure.
    45→
    46→**Pluggable handlers.** Each node type (LLM call, human gate, parallel fan-out) is backed by a handler that implements a common interface. New node types are added by registering new handlers. The execution engine does not know about handler internals.
    47→
    48→**Checkpoint and resume.** After each node completes, the execution engine saves a serializable checkpoint. If the process crashes, execution resumes from the last checkpoint.
    49→
    50→**Human-in-the-loop.** The pipeline can pause at designated nodes, present choices to a human operator, and route based on the human's decision. This supports approval gates, code review, and manual override -- critical for AI workflows where automated judgment may not be sufficient.
    51→
    52→**Edge-based routing.** Transitions between nodes are controlled by conditions, labels, and weights on edges, with runtime condition evaluation.
    53→
    54→### 1.4 Layering and LLM Backends
    55→
    56→Attractor defines the orchestration layer: graph definition, traversal, state management, and extensibility. It does NOT require any specific LLM integration. The codergen handler (Section 4.5) needs a way to call an LLM and get a response -- how you provide that is up to you.
    57→
    58→The codergen handler takes a backend that conforms to the `CodergenBackend` interface (Section 4.5). What that backend does internally is entirely up to the implementor -- use the companion [Coding Agent Loop](./coding-agent-loop-spec.md) and [Unified LLM Client](./unified-llm-spec.md) specs, spawn CLI agents (Claude Code, Codex, Gemini CLI) in subprocesses, run agents in tmux panes with a manager attaching to them, call an LLM API directly, or anything else. The pipeline definition (the DOT file) does not change regardless of backend choice.
    59→
    60→Attractor pipelines are driven by an event stream (Section 9.6). TUI, web, and IDE frontends consume events and submit human-in-the-loop answers. The pipeline engine is headless; the presentation layer is separate.

    64→## 2. DOT DSL Schema
    65→
    66→### 2.1 Supported Subset
    67→
    68→Attractor accepts a strict subset of the Graphviz DOT language. The restrictions exist for predictability: one graph per file, directed edges only, no HTML labels, and typed attributes with defaults.
    69→
    70→### 2.2 BNF-Style Grammar
    71→
    72→```
    73→Graph           ::= 'digraph' Identifier '{' Statement* '}'
    74→
    75→Statement       ::= GraphAttrStmt
    76→                   | NodeDefaults
    77→                   | EdgeDefaults
    78→                   | SubgraphStmt
    79→                   | NodeStmt
    80→                   | EdgeStmt
    81→                   | GraphAttrDecl
    82→
    83→GraphAttrStmt   ::= 'graph' AttrBlock ';'?
    84→NodeDefaults    ::= 'node' AttrBlock ';'?
    85→EdgeDefaults    ::= 'edge' AttrBlock ';'?
    86→GraphAttrDecl   ::= Identifier '=' Value ';'?
    87→
    88→SubgraphStmt    ::= 'subgraph' Identifier? '{' Statement* '}'
    89→
    90→NodeStmt        ::= Identifier AttrBlock? ';'?
    91→EdgeStmt        ::= Identifier ( '->' Identifier )+ AttrBlock? ';'?
    92→
    93→AttrBlock       ::= '[' Attr ( ',' Attr )* ']'
    94→Attr            ::= Key '=' Value
    95→
    96→Key             ::= Identifier | QualifiedId
    97→QualifiedId     ::= Identifier ( '.' Identifier )+
    98→
    99→Value           ::= String | Integer | Float | Boolean | Duration
   100→Identifier      ::= [A-Za-z_][A-Za-z0-9_]*
   101→String          ::= '"' ( '\\"' | '\\n' | '\\t' | '\\\\' | [^"\\] )* '"'
   102→Integer         ::= '-'? [0-9]+
   103→Float           ::= '-'? [0-9]* '.' [0-9]+
   104→Boolean         ::= 'true' | 'false'
   105→Duration        ::= Integer ( 'ms' | 's' | 'm' | 'h' | 'd' )
   106→
   107→Direction       ::= 'TB' | 'LR' | 'BT' | 'RL'
   108→```
   109→
   110→### 2.3 Key Constraints
   111→
   112→- **One digraph per file.** Multiple graphs, undirected graphs, and `strict` modifiers are rejected.
   113→- **Bare identifiers for node IDs.** Node IDs must match `[A-Za-z_][A-Za-z0-9_]*`. Human-readable names go in the `label` attribute.
   114→- **Commas required between attributes.** Inside attribute blocks, commas separate key-value pairs for unambiguous parsing.
   115→- **Directed edges only.** `->` is the only edge operator. `--` (undirected) is rejected.
   116→- **Comments supported.** Both `// line` and `/* block */` comments are stripped before parsing.
   117→- **Semicolons optional.** Statement-terminating semicolons are accepted but not required.
   118→
   119→### 2.4 Value Types
   120→
   121→| Type     | Syntax                          | Examples                             |
   122→|----------|---------------------------------|--------------------------------------|
   123→| String   | Double-quoted with escapes      | `"Hello world"`, `"line1\nline2"`    |
   124→| Integer  | Optional sign, digits           | `42`, `-1`, `0`                      |
   125→| Float    | Decimal number                  | `0.5`, `-3.14`                       |
   126→| Boolean  | Literal keywords                | `true`, `false`                      |
   127→| Duration | Integer + unit suffix           | `900s`, `15m`, `2h`, `250ms`, `1d`   |
   128→
   129→### 2.5 Graph-Level Attributes
   130→
   131→Graph attributes are declared in a `graph [ ... ]` block or as top-level `key = value` declarations. They configure the entire workflow.
   132→
   133→| Key                       | Type     | Default   | Description |
   134→|---------------------------|----------|-----------|-------------|
   135→| `goal`                    | String   | `""`      | Human-readable goal for the pipeline. Exposed as `$goal` in prompt templates and mirrored into the run context as `graph.goal`. |
   136→| `label`                   | String   | `""`      | Display name for the graph (used in visualization). |
   137→| `model_stylesheet`        | String   | `""`      | CSS-like stylesheet for per-node LLM model/provider defaults. See Section 8. |
   138→| `default_max_retry`       | Integer  | `50`      | Global retry ceiling for nodes that omit `max_retries`. |
   139→| `retry_target`            | String   | `""`      | Node ID to jump to if exit is reached with unsatisfied goal gates. |
   140→| `fallback_retry_target`   | String   | `""`      | Secondary jump target if `retry_target` is missing or invalid. |
   141→| `default_fidelity`        | String   | `""`      | Default context fidelity mode (see Section 5.4). |
   142→
   143→### 2.6 Node Attributes
   144→
   145→| Key                 | Type     | Default         | Description |
   146→|---------------------|----------|-----------------|-------------|
   147→| `label`             | String   | node ID         | Display name shown in UI, prompts, and telemetry. |
   148→| `shape`             | String   | `"box"`         | Graphviz shape. Determines the default handler type (see mapping table below). |
   149→| `type`              | String   | `""`            | Explicit handler type override. Takes precedence over shape-based resolution. |
   150→| `prompt`            | String   | `""`            | Primary instruction for the stage. Supports `$goal` variable expansion. Falls back to `label` if empty for LLM stages. |
   151→| `max_retries`       | Integer  | `0`             | Number of additional attempts beyond the initial execution. `max_retries=3` means up to 4 total executions. |
   152→| `goal_gate`         | Boolean  | `false`         | If `true`, this node must reach SUCCESS before the pipeline can exit. |
   153→| `retry_target`      | String   | `""`            | Node ID to jump to if this node fails and retries are exhausted. |
   154→| `fallback_retry_target` | String | `""`          | Secondary retry target. |
   155→| `fidelity`          | String   | inherited       | Context fidelity mode for this node's LLM session. See Section 5.4. |
   156→| `thread_id`         | String   | derived         | Explicit thread identifier for LLM session reuse under `full` fidelity. |
   157→| `class`             | String   | `""`            | Comma-separated class names for model stylesheet targeting. |
   158→| `timeout`           | Duration | unset           | Maximum execution time for this node. |
   159→| `llm_model`         | String   | inherited       | LLM model identifier. Overridable by stylesheet. |
   160→| `llm_provider`      | String   | auto-detected   | LLM provider key. Auto-detected from model if unset. |
   161→| `reasoning_effort`  | String   | `"high"`        | LLM reasoning effort: `low`, `medium`, `high`. |
   162→| `auto_status`       | Boolean  | `false`         | If `true` and the handler writes no status, the engine auto-generates a SUCCESS outcome. |
   163→| `allow_partial`     | Boolean  | `false`         | Accept PARTIAL_SUCCESS when retries are exhausted instead of failing. |
   164→
   165→### 2.7 Edge Attributes
   166→
   167→| Key          | Type     | Default | Description |
   168→|--------------|----------|---------|-------------|
   169→| `label`      | String   | `""`    | Human-facing caption and routing key. Used for preferred-label matching in edge selection. |
   170→| `condition`  | String   | `""`    | Boolean guard expression evaluated against the current context and outcome. See Section 10. |
   171→| `weight`     | Integer  | `0`     | Numeric priority for edge selection. Higher weight wins among equally eligible edges. |
   172→| `fidelity`   | String   | unset   | Override fidelity mode for the target node. Highest precedence in fidelity resolution. |
   173→| `thread_id`  | String   | unset   | Override thread ID for session reuse at the target node. |
   174→| `loop_restart` | Boolean | `false` | When `true`, terminates the current run and re-launches with a fresh log directory. |
   175→
   176→### 2.8 Shape-to-Handler-Type Mapping
   177→
   178→The `shape` attribute on a node determines which handler executes it, unless overridden by an explicit `type` attribute. This table defines the canonical mapping:
   179→
   180→| Shape             | Handler Type          | Description |
   181→|-------------------|-----------------------|-------------|
   182→| `Mdiamond`        | `start`               | Pipeline entry point. No-op handler. Every graph must have exactly one. |
   183→| `Msquare`         | `exit`                | Pipeline exit point. No-op handler. Every graph must have exactly one. |
   184→| `box`             | `codergen`            | LLM task (code generation, analysis, planning). The default for all nodes without an explicit shape. |
   185→| `hexagon`         | `wait.human`          | Human-in-the-loop gate. Blocks until a human selects an option. |
   186→| `diamond`         | `conditional`         | Conditional routing point. Routes based on edge conditions against current context. |
   187→| `component`       | `parallel`            | Parallel fan-out. Executes multiple branches concurrently. |
   188→| `tripleoctagon`   | `parallel.fan_in`     | Parallel fan-in. Waits for all branches and consolidates results. |
   189→| `parallelogram`   | `tool`                | External tool execution (shell command, API call). |
   190→| `house`           | `stack.manager_loop`  | Supervisor loop. Orchestrates observe/steer/wait cycles over a child pipeline. |
   191→
   192→### 2.9 Chained Edges
   193→
   194→Chained edge declarations are syntactic sugar. The statement:
   195→
   196→```
   197→A -> B -> C [label="next"]
   198→```
   199→
   200→expands to two edges:
   201→
   202→```
   203→A -> B [label="next"]
   204→B -> C [label="next"]
   205→```
   206→
   207→Edge attributes in a chained declaration apply to all edges in the chain.
   208→
   209→### 2.10 Subgraphs
   210→
   211→Subgraphs serve two purposes: **scoping defaults** and **deriving classes** for the model stylesheet.
   212→
   213→**Scoping defaults:** Attributes declared in a subgraph's `node [ ... ]` block apply to nodes within that subgraph unless the node explicitly overrides them.
   214→
   215→```
   216→subgraph cluster_loop {
   217→    label = "Loop A"
   218→    node [thread_id="loop-a", timeout="900s"]
   219→
   220→    Plan      [label="Plan next step"]
   221→    Implement [label="Implement", timeout="1800s"]
   222→}
   223→```
   224→
   225→Here `Plan` inherits `thread_id="loop-a"` and `timeout="900s"`, while `Implement` inherits `thread_id` but overrides `timeout`.
   226→
   227→**Class derivation:** Subgraph labels can produce CSS-like classes for model stylesheet matching. Nodes inside a subgraph receive the derived class. The class name is derived by lowercasing the label, replacing spaces with hyphens, and stripping non-alphanumeric characters (except hyphens). For example, `label="Loop A"` yields class `loop-a`.
   228→
   229→### 2.11 Node and Edge Default Blocks
   230→
   231→Default blocks set baseline attributes for all subsequent nodes or edges within their scope:
   232→
   233→```
   234→node [shape=box, timeout="900s"]
   235→edge [weight=0]
   236→```
   237→
   238→Explicit attributes on individual nodes or edges override these defaults.
   239→
   240→### 2.12 Class Attribute
   241→
   242→The `class` attribute assigns one or more CSS-like class names to a node for model stylesheet targeting:
   243→
   244→```
   245→review_code [shape=box, class="code,critical", prompt="Review the code"]
   246→```
   247→
   248→Classes are comma-separated. They can be referenced in the model stylesheet with dot-prefix selectors (`.code`, `.critical`).
   249→
   250→### 2.13 Minimal Examples
   251→
   252→**Simple linear workflow:**
   253→
   254→```
   255→digraph Simple {
   256→    graph [goal="Run tests and report"]
   257→    rankdir=LR
   258→
   259→    start [shape=Mdiamond, label="Start"]
   260→    exit  [shape=Msquare, label="Exit"]
   261→
   262→    run_tests [label="Run Tests", prompt="Run the test suite and report results"]
   263→    report    [label="Report", prompt="Summarize the test results"]
   264→
   265→    start -> run_tests -> report -> exit
   266→}
   267→```
   268→
   269→**Branching workflow with conditions:**
   270→
   271→```
   272→digraph Branch {
   273→    graph [goal="Implement and validate a feature"]
   274→    rankdir=LR
   275→    node [shape=box, timeout="900s"]
   276→
   277→    start     [shape=Mdiamond, label="Start"]
   278→    exit      [shape=Msquare, label="Exit"]
   279→    plan      [label="Plan", prompt="Plan the implementation"]
   280→    implement [label="Implement", prompt="Implement the plan"]
   281→    validate  [label="Validate", prompt="Run tests"]
   282→    gate      [shape=diamond, label="Tests passing?"]
   283→
   284→    start -> plan -> implement -> validate -> gate
   285→    gate -> exit      [label="Yes", condition="outcome=success"]
   286→    gate -> implement [label="No", condition="outcome!=success"]
   287→}
   288→```
   289→
   290→**Human gate:**
   291→
   292→```
   293→digraph Review {
   294→    rankdir=LR
   295→
   296→    start [shape=Mdiamond, label="Start"]
   297→    exit  [shape=Msquare, label="Exit"]
   298→
   299→    review_gate [
   300→        shape=hexagon,
   301→        label="Review Changes",
   302→        type="wait.human"
   303→    ]
   304→
   305→    start -> review_gate
   306→    review_gate -> ship_it [label="[A] Approve"]
   307→    review_gate -> fixes   [label="[F] Fix"]
   308→    ship_it -> exit
   309→    fixes -> review_gate
   310→}
   311→```

   315→## 3. Pipeline Execution Engine
   316→
   317→### 3.1 Run Lifecycle
   318→
   319→The execution lifecycle proceeds through five phases:
   320→
   321→```
   322→PARSE -> VALIDATE -> INITIALIZE -> EXECUTE -> FINALIZE
   323→```
   324→
   325→1. **Parse:** Read the `.dot` source and produce an in-memory Graph model (nodes, edges, attributes).
   326→2. **Validate:** Run lint rules (Section 7). Reject invalid graphs. Warn on suspicious patterns.
   327→3. **Initialize:** Create the run directory, initial context, and checkpoint. Mirror graph attributes into the context. Apply transforms (stylesheet, variable expansion).
   328→4. **Execute:** Traverse the graph from the start node, executing handlers and selecting edges.
   329→5. **Finalize:** Write the final checkpoint, emit completion events, and clean up resources (close sessions, release files).
   330→
   331→### 3.2 Core Execution Loop
   332→
   333→The following pseudocode defines the execution engine's traversal algorithm. This is the heart of the system.
   334→
   335→```
   336→FUNCTION run(graph, config):
   337→    context = new Context()
   338→    mirror_graph_attributes(graph, context)
   339→    checkpoint = new Checkpoint()
   340→    completed_nodes = []
   341→    node_outcomes = {}
   342→
   343→    current_node = find_start_node(graph)
   344→        -- Resolves by: (1) shape=Mdiamond, (2) id="start" or "Start"
   345→        -- Raises error if not found
   346→
   347→    WHILE true:
   348→        node = graph.nodes[current_node.id]
   349→
   350→        -- Step 1: Check for terminal node
   351→        IF is_terminal(node):
   352→            gate_ok, failed_gate = check_goal_gates(graph, node_outcomes)
   353→            IF NOT gate_ok AND failed_gate exists:
   354→                retry_target = get_retry_target(failed_gate, graph)
   355→                IF retry_target exists:
   356→                    current_node = graph.nodes[retry_target]
   357→                    CONTINUE
   358→                ELSE:
   359→                    RAISE "Goal gate unsatisfied and no retry target"
   360→            BREAK  -- Exit the loop; pipeline complete
   361→
   362→        -- Step 2: Execute node handler with retry policy
   363→        retry_policy = build_retry_policy(node, graph)
   364→        outcome = execute_with_retry(node, context, graph, retry_policy)
   365→
   366→        -- Step 3: Record completion
   367→        completed_nodes.append(node.id)
   368→        node_outcomes[node.id] = outcome
   369→
   370→        -- Step 4: Apply context updates from outcome
   371→        FOR EACH (key, value) IN outcome.context_updates:
   372→            context.set(key, value)
   373→        context.set("outcome", outcome.status)
   374→        IF outcome.preferred_label is not empty:
   375→            context.set("preferred_label", outcome.preferred_label)
   376→
   377→        -- Step 5: Save checkpoint
   378→        checkpoint = create_checkpoint(context, current_node.id, completed_nodes)
   379→        save_checkpoint(checkpoint, logs_root)
   380→
   381→        -- Step 6: Select next edge
   382→        next_edge = select_edge(node, outcome, context, graph)
   383→        IF next_edge is NONE:
   384→            IF outcome.status == FAIL:
   385→                RAISE "Stage failed with no outgoing fail edge"
   386→            BREAK
   387→
   388→        -- Step 7: Handle loop_restart
   389→        IF next_edge has loop_restart=true:
   390→            restart_run(graph, config, start_at=next_edge.target)
   391→            RETURN
   392→
   393→        -- Step 8: Advance to next node
   394→        current_node = graph.nodes[next_edge.to_node]
   395→
   396→    RETURN last_outcome
   397→```
   398→
   399→### 3.3 Edge Selection Algorithm
   400→
   401→After a node completes, the engine selects the next edge from the node's outgoing edges. The selection is deterministic and follows a five-step priority order:
   402→
   403→**Step 1: Condition-matching edges.** Evaluate each edge's `condition` expression (see Section 10) against the current context and outcome. Edges whose condition evaluates to `true` are eligible. Edges with no condition are not considered in this step; they proceed to later steps.
   404→
   405→**Step 2: Preferred label match.** If the node's outcome includes a `preferred_label`, find the first eligible edge (condition-passing or unconditional) whose `label` matches after normalization. Label normalization: lowercase, trim whitespace, strip accelerator prefixes (patterns like `[Y] `, `Y) `, `Y - `).
   406→
   407→**Step 3: Suggested next IDs.** If no label match and the outcome includes `suggested_next_ids`, find the first eligible edge whose target node ID appears in the list.
   408→
   409→**Step 4: Highest weight.** Among remaining eligible unconditional edges, choose the one with the highest `weight` attribute (default 0).
   410→
   411→**Step 5: Lexical tiebreak.** If weights are equal, choose the edge whose target node ID comes first lexicographically.
   412→
   413→```
   414→FUNCTION select_edge(node, outcome, context, graph):
   415→    edges = graph.outgoing_edges(node.id)
   416→    IF edges is empty:
   417→        RETURN NONE
   418→
   419→    -- Step 1: Condition matching
   420→    condition_matched = []
   421→    FOR EACH edge IN edges:
   422→        IF edge.condition is not empty:
   423→            IF evaluate_condition(edge.condition, outcome, context) == true:
   424→                condition_matched.append(edge)
   425→    IF condition_matched is not empty:
   426→        RETURN best_by_weight_then_lexical(condition_matched)
   427→
   428→    -- Step 2: Preferred label
   429→    IF outcome.preferred_label is not empty:
   430→        FOR EACH edge IN edges:
   431→            IF normalize_label(edge.label) == normalize_label(outcome.preferred_label):
   432→                RETURN edge
   433→
   434→    -- Step 3: Suggested next IDs
   435→    IF outcome.suggested_next_ids is not empty:
   436→        FOR EACH suggested_id IN outcome.suggested_next_ids:
   437→            FOR EACH edge IN edges:
   438→                IF edge.to_node == suggested_id:
   439→                    RETURN edge
   440→
   441→    -- Step 4 & 5: Weight with lexical tiebreak (unconditional edges only)
   442→    unconditional = [e FOR e IN edges WHERE e.condition is empty]
   443→    IF unconditional is not empty:
   444→        RETURN best_by_weight_then_lexical(unconditional)
   445→
   446→    -- Fallback: any edge
   447→    RETURN best_by_weight_then_lexical(edges)
   448→
   449→
   450→FUNCTION best_by_weight_then_lexical(edges):
   451→    SORT edges BY (weight DESCENDING, to_node ASCENDING)
   452→    RETURN edges[0]
   453→```
   454→
   455→### 3.4 Goal Gate Enforcement
   456→
   457→Nodes with `goal_gate=true` represent critical stages that must succeed before the pipeline can exit. When the traversal reaches a terminal node (shape=Msquare):
   458→
   459→1. Check all visited nodes that have `goal_gate=true`.
   460→2. If any goal gate node has a non-success outcome (not SUCCESS or PARTIAL_SUCCESS), the pipeline cannot exit.
   461→3. Instead, jump to the `retry_target` of the unsatisfied goal gate node. If that is not set, try `fallback_retry_target`. If that is also not set, try the graph-level `retry_target` and `fallback_retry_target`.
   462→4. If no retry target exists at any level, the pipeline fails with an error.
   463→
   464→```
   465→FUNCTION check_goal_gates(graph, node_outcomes):
   466→    FOR EACH (node_id, outcome) IN node_outcomes:
   467→        node = graph.nodes[node_id]
   468→        IF node.goal_gate == true:
   469→            IF outcome.status NOT IN {SUCCESS, PARTIAL_SUCCESS}:
   470→                RETURN (false, node)
   471→    RETURN (true, NONE)
   472→```
   473→
   474→### 3.5 Retry Logic
   475→
   476→Each node has a retry policy determined by:
   477→
   478→1. Node attribute `max_retries` (if set) -- number of additional attempts beyond the initial execution
   479→2. Graph attribute `default_max_retry` (fallback)
   480→3. Built-in default: 0 (no retries)
   481→
   482→The `max_retries` attribute specifies additional attempts. So `max_retries=3` means a total of 4 executions (1 initial + 3 retries). Internally this maps to `max_attempts = max_retries + 1`.
   483→
   484→```
   485→FUNCTION execute_with_retry(node, context, graph, retry_policy):
   486→    FOR attempt FROM 1 TO retry_policy.max_attempts:
   487→        TRY:
   488→            outcome = handler.execute(node, context, graph, logs_root)
   489→        CATCH exception:
   490→            IF retry_policy.should_retry(exception) AND attempt < retry_policy.max_attempts:
   491→                delay = retry_policy.backoff.delay_for_attempt(attempt)
   492→                sleep(delay)
   493→                CONTINUE
   494→            ELSE:
   495→                RETURN Outcome(status=FAIL, failure_reason=str(exception))
   496→
   497→        IF outcome.status IN {SUCCESS, PARTIAL_SUCCESS}:
   498→            reset_retry_counter(node.id)
   499→            RETURN outcome
   500→
   501→        IF outcome.status == RETRY:
   502→            IF attempt < retry_policy.max_attempts:
   503→                increment_retry_counter(node.id)
   504→                delay = retry_policy.backoff.delay_for_attempt(attempt)
   505→                sleep(delay)
   506→                CONTINUE
   507→            ELSE:
   508→                IF node.allow_partial == true:
   509→                    RETURN Outcome(status=PARTIAL_SUCCESS, notes="retries exhausted, partial accepted")
   510→                RETURN Outcome(status=FAIL, failure_reason="max retries exceeded")
   511→
   512→        IF outcome.status == FAIL:
   513→            RETURN outcome
   514→
   515→    RETURN Outcome(status=FAIL, failure_reason="max retries exceeded")
   516→```
   517→
   518→### 3.6 Retry Policy
   519→
   520→```
   521→RetryPolicy:
   522→    max_attempts    : Integer         -- minimum 1 (1 means no retries)
   523→    backoff         : BackoffConfig   -- delay calculation between retries
   524→    should_retry    : Function(Error) -> Boolean  -- predicate for retryable errors
   525→
   526→BackoffConfig:
   527→    initial_delay_ms  : Integer   -- first retry delay in milliseconds (default: 200)
   528→    backoff_factor    : Float     -- multiplier for subsequent delays (default: 2.0)
   529→    max_delay_ms      : Integer   -- cap on delay in milliseconds (default: 60000)
   530→    jitter            : Boolean   -- add random jitter to prevent thundering herd (default: true)
   531→```
   532→
   533→**Delay calculation:**
   534→
   535→```
   536→FUNCTION delay_for_attempt(attempt, config):
   537→    -- attempt is 1-indexed (first retry is attempt=1)
   538→    delay = config.initial_delay_ms * (config.backoff_factor ^ (attempt - 1))
   539→    delay = MIN(delay, config.max_delay_ms)
   540→    IF config.jitter:
   541→        delay = delay * random_uniform(0.5, 1.5)
   542→    RETURN delay
   543→```
   544→
   545→**Preset policies:**
   546→
   547→| Name         | Max Attempts | Initial Delay | Factor | Description |
   548→|--------------|-------------|---------------|--------|-------------|
   549→| `none`       | 1           | --            | --     | No retries. Fail immediately on error. |
   550→| `standard`   | 5           | 200ms         | 2.0    | General-purpose. Delays: 200, 400, 800, 1600, 3200ms. |
   551→| `aggressive`  | 5           | 500ms         | 2.0    | For unreliable operations. Delays: 500, 1000, 2000, 4000, 8000ms. |
   552→| `linear`     | 3           | 500ms         | 1.0    | Fixed delay between attempts. Delays: 500, 500, 500ms. |
   553→| `patient`    | 3           | 2000ms        | 3.0    | Long-running operations. Delays: 2000, 6000, 18000ms. |
   554→
   555→**Default should_retry predicate:** Returns `true` for network errors, rate limit errors (HTTP 429), server errors (HTTP 5xx), and provider-reported transient failures. Returns `false` for authentication errors (HTTP 401, 403), bad request errors (HTTP 400), validation errors, and configuration errors.
   556→
   557→### 3.7 Failure Routing
   558→
   559→When a stage returns FAIL (or retries are exhausted), the engine attempts failure routing in this order:
   560→
   561→1. **Fail edge:** An outgoing edge with `condition="outcome=fail"`. If found, follow it.
   562→2. **Retry target:** Node attribute `retry_target`. Jump to that node.
   563→3. **Fallback retry target:** Node attribute `fallback_retry_target`. Jump to that node.
   564→4. **Pipeline termination:** No failure route found. The pipeline fails with the stage's failure reason.
   565→
   566→### 3.8 Concurrency Model
   567→
   568→The graph traversal is single-threaded. Only one node executes at a time in the top-level graph. This simplifies reasoning about context state and avoids race conditions.
   569→
   570→Parallelism exists within specific node handlers (`parallel`, `parallel.fan_in`) that manage concurrent execution internally. Each parallel branch receives an isolated clone of the context. Branch results are collected but individual branch context changes are not merged back into the parent -- only the handler's outcome and its `context_updates` are applied.

   574→## 4. Node Handlers
   575→
   576→### 4.1 Handler Interface
   577→
   578→Every node handler implements a common interface. The execution engine dispatches to the appropriate handler based on the node's `type` attribute (or shape-based resolution if `type` is empty).
   579→
   580→```
   581→INTERFACE Handler:
   582→    FUNCTION execute(node, context, graph, logs_root) -> Outcome
   583→
   584→    -- Parameters:
   585→    --   node      : The parsed Node with all its attributes
   586→    --   context   : The shared key-value Context for the pipeline run (read/write)
   587→    --   graph     : The full parsed Graph (for reading outgoing edges, etc.)
   588→    --   logs_root : Filesystem path for this run's log/artifact directory
   589→
   590→    -- Returns:
   591→    --   Outcome   : The result of execution (see Section 5.2)
   592→```
   593→
   594→### 4.2 Handler Registry
   595→
   596→The handler registry maps type strings to handler instances. Resolution follows this order:
   597→
   598→1. **Explicit `type` attribute** on the node (e.g., `type="wait.human"`)
   599→2. **Shape-based resolution** using the shape-to-handler-type mapping table (Section 2.8)
   600→3. **Default handler** (the codergen/LLM handler)
   601→
   602→```
   603→HandlerRegistry:
   604→    handlers        : Map<String, Handler>   -- type string -> handler instance
   605→    default_handler : Handler                -- fallback handler (typically codergen)
   606→
   607→    FUNCTION register(type_string, handler):
   608→        handlers[type_string] = handler
   609→        -- Registering for an already-registered type replaces the previous handler
   610→
   611→    FUNCTION resolve(node) -> Handler:
   612→        -- 1. Explicit type attribute
   613→        IF node.type is not empty AND node.type IN handlers:
   614→            RETURN handlers[node.type]
   615→
   616→        -- 2. Shape-based resolution
   617→        handler_type = SHAPE_TO_TYPE[node.shape]
   618→        IF handler_type IN handlers:
   619→            RETURN handlers[handler_type]
   620→
   621→        -- 3. Default
   622→        RETURN default_handler
   623→```
   624→
   625→### 4.3 Start Handler
   626→
   627→A no-op handler for the pipeline entry point. Returns SUCCESS immediately without performing any work.
   628→
   629→```
   630→StartHandler:
   631→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   632→        RETURN Outcome(status=SUCCESS)
   633→```
   634→
   635→Every graph must have exactly one start node (shape=Mdiamond). The lint rules enforce this.
   636→
   637→### 4.4 Exit Handler
   638→
   639→A no-op handler for the pipeline exit point. Returns SUCCESS immediately. Goal gate enforcement is handled by the execution engine (Section 3.4), not by this handler.
   640→
   641→```
   642→ExitHandler:
   643→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   644→        RETURN Outcome(status=SUCCESS)
   645→```
   646→
   647→Every graph must have exactly one exit node (shape=Msquare).
   648→
   649→### 4.5 Codergen Handler (LLM Task)
   650→
   651→The codergen handler is the default for all nodes that invoke an LLM. It reads the node's prompt, expands template variables, calls the LLM backend (see Section 1.4 for backend options), writes the prompt and response to the logs directory, and returns the outcome.
   652→
   653→```
   654→CodergenHandler:
   655→    backend : CodergenBackend | None
   656→        -- The LLM execution backend. Any implementation of the
   657→        -- CodergenBackend interface (Section 4.5). None = simulation mode.
   658→
   659→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   660→        -- 1. Build prompt
   661→        prompt = node.prompt
   662→        IF prompt is empty:
   663→            prompt = node.label
   664→        prompt = expand_variables(prompt, graph, context)
   665→
   666→        -- 2. Write prompt to logs
   667→        stage_dir = logs_root + "/" + node.id + "/"
   668→        create_directory(stage_dir)
   669→        write_file(stage_dir + "prompt.md", prompt)
   670→
   671→        -- 3. Call LLM backend
   672→        IF backend is not NONE:
   673→            TRY:
   674→                result = backend.run(node, prompt, context)
   675→                IF result is an Outcome:
   676→                    write_status(stage_dir, result)
   677→                    RETURN result
   678→                response_text = string(result)
   679→            CATCH exception:
   680→                RETURN Outcome(status=FAIL, failure_reason=str(exception))
   681→        ELSE:
   682→            response_text = "[Simulated] Response for stage: " + node.id
   683→
   684→        -- 4. Write response to logs
   685→        write_file(stage_dir + "response.md", response_text)
   686→
   687→        -- 5. Write status and return outcome
   688→        outcome = Outcome(
   689→            status=SUCCESS,
   690→            notes="Stage completed: " + node.id,
   691→            context_updates={
   692→                "last_stage": node.id,
   693→                "last_response": truncate(response_text, 200)
   694→            }
   695→        )
   696→        write_status(stage_dir, outcome)
   697→        RETURN outcome
   698→```
   699→
   700→**Variable expansion:** The only built-in template variable is `$goal`, which resolves to the graph-level `goal` attribute. Variable expansion is simple string replacement, not a templating engine.
   701→
   702→**Status file:** The handler writes `status.json` in the stage directory with the Outcome fields serialized as JSON. This file serves as an audit trail and enables the status-file contract: external tools or agents can write `status.json` to communicate outcomes back to the engine.
   703→
   704→#### CodergenBackend Interface
   705→
   706→```
   707→INTERFACE CodergenBackend:
   708→    FUNCTION run(node: Node, prompt: String, context: Context) -> String | Outcome
   709→```
   710→
   711→How you implement this interface is up to you. The pipeline engine only cares that it gets a String or Outcome back.
   712→
   713→### 4.6 Wait For Human Handler
   714→
   715→Blocks pipeline execution until a human selects an option derived from the node's outgoing edges. This implements the human-in-the-loop pattern (see Section 6 for the full Interviewer protocol).
   716→
   717→```
   718→WaitForHumanHandler:
   719→    interviewer : Interviewer  -- the human interaction frontend
   720→
   721→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   722→        -- 1. Derive choices from outgoing edges
   723→        edges = graph.outgoing_edges(node.id)
   724→        choices = []
   725→        FOR EACH edge IN edges:
   726→            label = edge.label OR edge.to_node
   727→            key = parse_accelerator_key(label)
   728→            choices.append(Choice(key=key, label=label, to=edge.to_node))
   729→
   730→        IF choices is empty:
   731→            RETURN Outcome(status=FAIL, failure_reason="No outgoing edges for human gate")
   732→
   733→        -- 2. Build question from choices
   734→        options = [Option(key=c.key, label=c.label) FOR c IN choices]
   735→        question = Question(
   736→            text=node.label OR "Select an option:",
   737→            type=MULTIPLE_CHOICE,
   738→            options=options,
   739→            stage=node.id
   740→        )
   741→
   742→        -- 3. Present to interviewer and wait for answer
   743→        answer = interviewer.ask(question)
   744→
   745→        -- 4. Handle timeout/skip
   746→        IF answer is TIMEOUT:
   747→            default_choice = node.attrs["human.default_choice"]
   748→            IF default_choice exists:
   749→                -- Use default
   750→            ELSE:
   751→                RETURN Outcome(status=RETRY, failure_reason="human gate timeout, no default")
   752→
   753→        IF answer is SKIPPED:
   754→            RETURN Outcome(status=FAIL, failure_reason="human skipped interaction")
   755→
   756→        -- 5. Find matching choice
   757→        selected = find_choice_matching(answer, choices)
   758→        IF selected is NONE:
   759→            selected = choices[0]  -- fallback to first
   760→
   761→        -- 6. Record in context and return
   762→        RETURN Outcome(
   763→            status=SUCCESS,
   764→            suggested_next_ids=[selected.to],
   765→            context_updates={
   766→                "human.gate.selected": selected.key,
   767→                "human.gate.label": selected.label
   768→            }
   769→        )
   770→```
   771→
   772→**Accelerator key parsing** extracts shortcut keys from edge labels using these patterns:
   773→
   774→| Pattern           | Example           | Extracted Key |
   775→|-------------------|-------------------|---------------|
   776→| `[K] Label`       | `[Y] Yes, deploy` | `Y`           |
   777→| `K) Label`        | `Y) Yes, deploy`  | `Y`           |
   778→| `K - Label`       | `Y - Yes, deploy` | `Y`           |
   779→| First character   | `Yes, deploy`     | `Y`           |
   780→
   781→### 4.7 Conditional Handler
   782→
   783→For diamond-shaped nodes that act as conditional routing points. The handler itself is a no-op that returns SUCCESS; the actual routing is handled by the execution engine's edge selection algorithm (Section 3.3), which evaluates conditions on outgoing edges.
   784→
   785→```
   786→ConditionalHandler:
   787→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   788→        RETURN Outcome(
   789→            status=SUCCESS,
   790→            notes="Conditional node evaluated: " + node.id
   791→        )
   792→```
   793→
   794→This design keeps routing logic in the engine (where it can be deterministic and inspectable) rather than in the handler.
   795→
   796→### 4.8 Parallel Handler
   797→
   798→Fans out execution to multiple branches concurrently. Each parallel branch receives an isolated clone of the parent context and runs independently. The handler waits for all branches to complete (or applies a configurable join policy) before returning.
   799→
   800→```
   801→ParallelHandler:
   802→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   803→        -- 1. Identify fan-out edges (all outgoing edges from this node)
   804→        branches = graph.outgoing_edges(node.id)
   805→
   806→        -- 2. Determine join policy from node attributes
   807→        join_policy = node.attrs.get("join_policy", "wait_all")
   808→        error_policy = node.attrs.get("error_policy", "continue")
   809→        max_parallel = integer(node.attrs.get("max_parallel", "4"))
   810→
   811→        -- 3. Execute branches concurrently with bounded parallelism
   812→        results = []
   813→        FOR EACH branch IN branches (up to max_parallel at a time):
   814→            branch_context = context.clone()
   815→            branch_outcome = execute_subgraph(branch.to_node, branch_context, graph, logs_root)
   816→            results.append(branch_outcome)
   817→
   818→        -- 4. Evaluate join policy
   819→        success_count = count(r FOR r IN results WHERE r.status == SUCCESS)
   820→        fail_count = count(r FOR r IN results WHERE r.status == FAIL)
   821→
   822→        IF join_policy == "wait_all":
   823→            IF fail_count == 0:
   824→                RETURN Outcome(status=SUCCESS)
   825→            ELSE:
   826→                RETURN Outcome(status=PARTIAL_SUCCESS)
   827→
   828→        IF join_policy == "first_success":
   829→            IF success_count > 0:
   830→                RETURN Outcome(status=SUCCESS)
   831→            ELSE:
   832→                RETURN Outcome(status=FAIL)
   833→
   834→        -- 5. Store results in context for downstream fan-in
   835→        context.set("parallel.results", serialize_results(results))
   836→        RETURN Outcome(status=SUCCESS)
   837→```
   838→
   839→**Join policies:**
   840→
   841→| Policy           | Behavior |
   842→|------------------|----------|
   843→| `wait_all`       | All branches must complete. Join satisfied when all are done. |
   844→| `k_of_n`         | At least K branches must succeed. |
   845→| `first_success`  | Join satisfied as soon as one branch succeeds. Others may be cancelled. |
   846→| `quorum`         | At least a configurable fraction of branches must succeed. |
   847→
   848→**Error policies:**
   849→
   850→| Policy              | Behavior |
   851→|---------------------|----------|
   852→| `fail_fast`         | Cancel all remaining branches on first failure. |
   853→| `continue`          | Continue remaining branches. Collect all results. |
   854→| `ignore`            | Ignore failures entirely. Return only successful results. |
   855→
   856→### 4.9 Fan-In Handler
   857→
   858→Consolidates results from a preceding parallel node and selects the best candidate.
   859→
   860→```
   861→FanInHandler:
   862→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   863→        -- 1. Read parallel results
   864→        results = context.get("parallel.results")
   865→        IF results is empty:
   866→            RETURN Outcome(status=FAIL, failure_reason="No parallel results to evaluate")
   867→
   868→        -- 2. Evaluate candidates
   869→        IF node.prompt is not empty:
   870→            -- LLM-based evaluation: call LLM to rank candidates
   871→            best = llm_evaluate(node.prompt, results)
   872→        ELSE:
   873→            -- Heuristic: rank by outcome status, then by score
   874→            best = heuristic_select(results)
   875→
   876→        -- 3. Record winner in context
   877→        context_updates = {
   878→            "parallel.fan_in.best_id": best.id,
   879→            "parallel.fan_in.best_outcome": best.outcome
   880→        }
   881→
   882→        RETURN Outcome(
   883→            status=SUCCESS,
   884→            context_updates=context_updates,
   885→            notes="Selected best candidate: " + best.id
   886→        )
   887→
   888→
   889→FUNCTION heuristic_select(candidates):
   890→    outcome_rank = {SUCCESS: 0, PARTIAL_SUCCESS: 1, RETRY: 2, FAIL: 3}
   891→    SORT candidates BY (outcome_rank[c.outcome], -c.score, c.id)
   892→    RETURN candidates[0]
   893→```
   894→
   895→Fan-in runs even when some candidates failed, as long as at least one candidate is available. Only when all candidates fail does fan-in return FAIL.
   896→
   897→### 4.10 Tool Handler
   898→
   899→Executes an external tool (shell command, API call, or other non-LLM operation) configured via node attributes.
   900→
   901→```
   902→ToolHandler:
   903→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   904→        command = node.attrs.get("tool_command", "")
   905→        IF command is empty:
   906→            RETURN Outcome(status=FAIL, failure_reason="No tool_command specified")
   907→
   908→        -- Execute the command
   909→        TRY:
   910→            result = run_shell_command(command, timeout=node.timeout)
   911→            RETURN Outcome(
   912→                status=SUCCESS,
   913→                context_updates={"tool.output": result.stdout},
   914→                notes="Tool completed: " + command
   915→            )
   916→        CATCH exception:
   917→            RETURN Outcome(status=FAIL, failure_reason=str(exception))
   918→```

   920→### 4.11 Manager Loop Handler
   921→
   922→Orchestrates sprint-based iteration by supervising a child pipeline. The manager observes the child's telemetry, evaluates progress via a guard function, and optionally steers the child through intervention.
   923→
   924→```
   925→ManagerLoopHandler:
   926→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   927→        child_dotfile = graph.attrs.get("stack.child_dotfile")
   928→        poll_interval = parse_duration(node.attrs.get("manager.poll_interval", "45s"))
   929→        max_cycles = integer(node.attrs.get("manager.max_cycles", "1000"))
   930→        stop_condition = node.attrs.get("manager.stop_condition", "")
   931→        actions = split(node.attrs.get("manager.actions", "observe,wait"), ",")
   932→
   933→        -- 1. Auto-start child if configured
   934→        IF node.attrs.get("stack.child_autostart", "true") == "true":
   935→            start_child_pipeline(child_dotfile)
   936→
   937→        -- 2. Observation loop
   938→        FOR cycle FROM 1 TO max_cycles:
   939→            IF "observe" IN actions:
   940→                ingest_child_telemetry(context)
   941→
   942→            IF "steer" IN actions AND steer_cooldown_elapsed():
   943→                steer_child(context, node)
   944→
   945→            -- Evaluate stop conditions
   946→            child_status = context.get_string("context.stack.child.status")
   947→            IF child_status IN {"completed", "failed"}:
   948→                child_outcome = context.get_string("context.stack.child.outcome")
   949→                IF child_outcome == "success":
   950→                    RETURN Outcome(status=SUCCESS, notes="Child completed")
   951→                IF child_status == "failed":
   952→                    RETURN Outcome(status=FAIL, failure_reason="Child failed")
   953→
   954→            IF stop_condition is not empty:
   955→                IF evaluate_condition(stop_condition, ..., context):
   956→                    RETURN Outcome(status=SUCCESS, notes="Stop condition satisfied")
   957→
   958→            IF "wait" IN actions:
   959→                sleep(poll_interval)
   960→
   961→        RETURN Outcome(status=FAIL, failure_reason="Max cycles exceeded")
   962→```
   963→
   964→The manager pattern implements a **supervisor architecture** where:
   965→- **Observe** ingests worker telemetry (active stage, outcomes, retry counts, artifacts)
   966→- **Guard** scores worker progress and routes to continue, intervene, or escalate
   967→- **Steer** writes intervention instructions to the child's active stage directory
   968→
   969→### 4.12 Custom Handlers
   970→
   971→New handler types are added by implementing the Handler interface and registering with the registry:
   972→
   973→```
   974→-- Define a custom handler
   975→MyCustomHandler:
   976→    FUNCTION execute(node, context, graph, logs_root) -> Outcome:
   977→        -- Custom logic here
   978→        RETURN Outcome(status=SUCCESS)
   979→
   980→-- Register it
   981→registry.register("my_custom_type", MyCustomHandler())
   982→
   983→-- Reference in DOT file
   984→my_node [type="my_custom_type", shape=box, custom_attr="value"]
   985→```
   986→
   987→**Handler contract:**
   988→- Handlers MUST be stateless or protect shared mutable state with synchronization.
   989→- Handler panics/exceptions MUST be caught by the engine and converted to FAIL outcomes.
   990→- Handlers SHOULD NOT embed provider-specific logic; LLM orchestration is delegated to the integrated SDK.

   994→## 5. State and Context
   995→
   996→### 5.1 Context
   997→
   998→The context is a thread-safe key-value store shared across all stages during a pipeline run. It is the primary mechanism for passing data between nodes.
   999→
  1000→```
  1001→Context:
  1002→    values : Map<String, Any>      -- key-value store
  1003→    lock   : ReadWriteLock         -- thread safety for parallel access
  1004→    logs   : List<String>          -- append-only run log
  1005→
  1006→    FUNCTION set(key, value):
  1007→        ACQUIRE write lock
  1008→        values[key] = value
  1009→        RELEASE write lock
  1010→
  1011→    FUNCTION get(key, default=NONE) -> Any:
  1012→        ACQUIRE read lock
  1013→        result = values.get(key, default)
  1014→        RELEASE read lock
  1015→        RETURN result
  1016→
  1017→    FUNCTION get_string(key, default="") -> String:
  1018→        value = get(key)
  1019→        IF value is NONE: RETURN default
  1020→        RETURN string(value)
  1021→
  1022→    FUNCTION append_log(entry):
  1023→        ACQUIRE write lock
  1024→        logs.append(entry)
  1025→        RELEASE write lock
  1026→
  1027→    FUNCTION snapshot() -> Map<String, Any>:
  1028→        -- Returns a serializable copy of all values
  1029→        ACQUIRE read lock
  1030→        result = shallow_copy(values)
  1031→        RELEASE read lock
  1032→        RETURN result
  1033→
  1034→    FUNCTION clone() -> Context:
  1035→        -- Deep copy for parallel branch isolation
  1036→        ACQUIRE read lock
  1037→        new_context = new Context()
  1038→        new_context.values = shallow_copy(values)
  1039→        new_context.logs = copy(logs)
  1040→        RELEASE read lock
  1041→        RETURN new_context
  1042→
  1043→    FUNCTION apply_updates(updates):
  1044→        -- Merge a dictionary of updates into the context
  1045→        ACQUIRE write lock
  1046→        FOR EACH (key, value) IN updates:
  1047→            values[key] = value
  1048→        RELEASE write lock
  1049→```
  1050→
  1051→**Built-in context keys set by the engine:**
  1052→
  1053→| Key                                   | Type    | Set By   | Description |
  1054→|---------------------------------------|---------|----------|-------------|
  1055→| `outcome`                             | String  | Engine   | Last handler outcome status (`success`, `fail`, etc.) |
  1056→| `preferred_label`                     | String  | Engine   | Last handler's preferred edge label |
  1057→| `graph.goal`                          | String  | Engine   | Mirrored from graph `goal` attribute |
  1058→| `current_node`                        | String  | Engine   | ID of the currently executing node |
  1059→| `last_stage`                          | String  | Handler  | ID of the last completed stage |
  1060→| `last_response`                       | String  | Handler  | Truncated text of the last LLM response |
  1061→| `internal.retry_count.<node_id>`      | Integer | Engine   | Retry counter for a specific node |
  1062→
  1063→**Context key namespace conventions:**
  1064→
  1065→| Prefix        | Purpose                                        |
  1066→|---------------|------------------------------------------------|
  1067→| `context.*`   | Semantic state shared between nodes            |
  1068→| `graph.*`     | Graph attributes mirrored at initialization    |
  1069→| `internal.*`  | Engine bookkeeping (retry counters, timing)    |
  1070→| `parallel.*`  | Parallel handler state (results, counts)       |
  1071→| `stack.*`     | Supervisor/worker state                        |
  1072→| `human.gate.*`| Human interaction state                        |
  1073→| `work.*`      | Per-item context for parallel work items       |
  1074→
  1075→### 5.2 Outcome
  1076→
  1077→The outcome is the result of executing a node handler. It drives routing decisions and state updates.
  1078→
  1079→```
  1080→Outcome:
  1081→    status             : StageStatus     -- SUCCESS, FAIL, PARTIAL_SUCCESS, RETRY, SKIPPED
  1082→    preferred_label    : String          -- which edge label to follow (optional)
  1083→    suggested_next_ids : List<String>    -- explicit next node IDs (optional)
  1084→    context_updates    : Map<String, Any> -- key-value pairs to merge into context
  1085→    notes              : String          -- human-readable execution summary
  1086→    failure_reason     : String          -- reason for failure (when status is FAIL or RETRY)
  1087→```
  1088→
  1089→**StageStatus values:**
  1090→
  1091→| Status             | Meaning |
  1092→|--------------------|---------|
  1093→| `SUCCESS`          | Stage completed its work. Proceed to next edge. Reset retry counter. |
  1094→| `PARTIAL_SUCCESS`  | Stage completed with caveats. Treated as success for routing but notes describe what was incomplete. |
  1095→| `RETRY`            | Stage requests re-execution. Engine increments retry counter and re-executes if within limits. |
  1096→| `FAIL`             | Stage failed permanently. Engine looks for a fail edge or terminates the pipeline. |
  1097→| `SKIPPED`          | Stage was skipped (e.g., condition not met). Proceed without recording an outcome. |
  1098→
  1099→### 5.3 Checkpoint
  1100→
  1101→A serializable snapshot of execution state, saved after each node completes. Enables crash recovery and resume.
  1102→
  1103→```
  1104→Checkpoint:
  1105→    timestamp       : Timestamp              -- when this checkpoint was created
  1106→    current_node    : String                  -- ID of the last completed node
  1107→    completed_nodes : List<String>            -- IDs of all completed nodes in order
  1108→    node_retries    : Map<String, Integer>    -- retry counters per node
  1109→    context_values  : Map<String, Any>        -- serialized snapshot of the context
  1110→    logs            : List<String>            -- run log entries
  1111→
  1112→    FUNCTION save(path):
  1113→        -- Serialize to JSON and write to filesystem
  1114→        data = {
  1115→            "timestamp": timestamp,
  1116→            "current_node": current_node,
  1117→            "completed_nodes": completed_nodes,
  1118→            "node_retries": node_retries,
  1119→            "context": serialize_to_json(context_values),
  1120→            "logs": logs
  1121→        }
  1122→        write_json_file(path, data)
  1123→
  1124→    FUNCTION load(path) -> Checkpoint:
  1125→        -- Deserialize from JSON file
  1126→        data = read_json_file(path)
  1127→        RETURN new Checkpoint from data
  1128→```
  1129→
  1130→**Resume behavior:**
  1131→
  1132→1. Load the checkpoint from `{logs_root}/checkpoint.json`.
  1133→2. Restore context state from `context_values`.
  1134→3. Restore `completed_nodes` to skip already-finished work.
  1135→4. Restore retry counters from `node_retries`.
  1136→5. Determine the next node to execute (the one after `current_node` in the traversal).
  1137→6. If the previous node used `full` fidelity, degrade to `summary:high` for the first resumed node, because in-memory LLM sessions cannot be serialized. After this one degraded hop, subsequent nodes may use `full` fidelity again.
  1138→
  1139→### 5.4 Context Fidelity
  1140→
  1141→Context fidelity controls how much prior conversation and state is carried into the next node's LLM session. This is a core mechanism for managing context window usage across multi-stage pipelines.
  1142→
  1143→```
  1144→FidelityMode ::= 'full'
  1145→               | 'truncate'
  1146→               | 'compact'
  1147→               | 'summary:low'
  1148→               | 'summary:medium'
  1149→               | 'summary:high'
  1150→```
  1151→
  1152→| Mode             | Session | Context Carried                                         | Approximate Token Budget |
  1153→|------------------|---------|---------------------------------------------------------|--------------------------|
  1154→| `full`           | Reused (same thread) | Full conversation history preserved                      | Unbounded (uses compaction) |
  1155→| `truncate`       | Fresh   | Minimal: only graph goal and run ID                      | Minimal |
  1156→| `compact`        | Fresh   | Structured bullet-point summary: completed stages, outcomes, key context values | Moderate |
  1157→| `summary:low`    | Fresh   | Brief textual summary with minimal event counts          | ~600 tokens |
  1158→| `summary:medium` | Fresh   | Moderate detail: recent stage outcomes, active context values, notable events | ~1500 tokens |
  1159→| `summary:high`   | Fresh   | Detailed: many recent events, tool call summaries, comprehensive context | ~3000 tokens |
  1160→
  1161→**Fidelity resolution precedence (highest to lowest):**
  1162→
  1163→1. Edge `fidelity` attribute (on the incoming edge)
  1164→2. Target node `fidelity` attribute
  1165→3. Graph `default_fidelity` attribute
  1166→4. Default: `compact`
  1167→
  1168→**Thread resolution (for `full` fidelity):**
  1169→
  1170→When fidelity resolves to `full`, the engine determines a thread key for session reuse:
  1171→
  1172→1. Target node `thread_id` attribute
  1173→2. Edge `thread_id` attribute
  1174→3. Graph-level default thread
  1175→4. Derived class from enclosing subgraph
  1176→5. Fallback: previous node ID
  1177→
  1178→Nodes that share the same thread key reuse the same LLM session. Nodes with different thread keys start fresh sessions.
  1179→
  1180→### 5.5 Artifact Store
  1181→
  1182→The artifact store provides named, typed storage for large stage outputs that do not belong in the context (which should contain only small scalar values for routing and checkpoint serialization).
  1183→
  1184→```
  1185→ArtifactStore:
  1186→    artifacts : Map<String, (ArtifactInfo, Any)>
  1187→    lock      : ReadWriteLock
  1188→    base_dir  : String or NONE   -- filesystem directory for file-backed artifacts
  1189→
  1190→    FUNCTION store(artifact_id, name, data) -> ArtifactInfo:
  1191→        size = byte_size(data)
  1192→        is_file_backed = (size > FILE_BACKING_THRESHOLD) AND (base_dir is not NONE)
  1193→        IF is_file_backed:
  1194→            write data to "{base_dir}/artifacts/{artifact_id}.json"
  1195→            stored_data = file_path
  1196→        ELSE:
  1197→            stored_data = data
  1198→        info = ArtifactInfo(id=artifact_id, name=name, size=size, is_file_backed=is_file_backed)
  1199→        artifacts[artifact_id] = (info, stored_data)
  1200→        RETURN info
  1201→
  1202→    FUNCTION retrieve(artifact_id) -> Any:
  1203→        IF artifact_id NOT IN artifacts:
  1204→            RAISE "Artifact not found"
  1205→        (info, data) = artifacts[artifact_id]
  1206→        IF info.is_file_backed:
  1207→            RETURN read_json_file(data)
  1208→        RETURN data
  1209→
  1210→    FUNCTION has(artifact_id) -> Boolean
  1211→    FUNCTION list() -> List<ArtifactInfo>
  1212→    FUNCTION remove(artifact_id)
  1213→    FUNCTION clear()
  1214→
  1215→ArtifactInfo:
  1216→    id              : String
  1217→    name            : String
  1218→    size_bytes      : Integer
  1219→    stored_at       : Timestamp
  1220→    is_file_backed  : Boolean
  1221→```
  1222→
  1223→The default file-backing threshold is 100KB. Artifacts below this threshold are stored in memory; above it, they are written to disk.
  1224→
  1225→### 5.6 Run Directory Structure
  1226→
  1227→Each pipeline execution produces a directory tree for logging, checkpoints, and artifacts:
  1228→
  1229→```
  1230→{logs_root}/
  1231→    checkpoint.json              -- Serialized checkpoint after each node
  1232→    manifest.json                -- Pipeline metadata (name, goal, start time)
  1233→    {node_id}/
  1234→        status.json              -- Node execution outcome
  1235→        prompt.md                -- Rendered prompt sent to LLM
  1236→        response.md              -- LLM response text
  1237→    artifacts/
  1238→        {artifact_id}.json       -- File-backed artifacts
  1239→```

  1243→## 6. Human-in-the-Loop (Interviewer Pattern)
  1244→
  1245→### 6.1 Interviewer Interface
  1246→
  1247→All human interaction in Attractor goes through an Interviewer interface. This abstraction allows the pipeline to present questions to a human and receive answers through any frontend: CLI, web UI, Slack bot, or a programmatic queue for testing.
  1248→
  1249→```
  1250→INTERFACE Interviewer:
  1251→    FUNCTION ask(question: Question) -> Answer
  1252→    FUNCTION ask_multiple(questions: List<Question>) -> List<Answer>
  1253→    FUNCTION inform(message: String, stage: String) -> Void
  1254→```
  1255→
  1256→### 6.2 Question Model
  1257→
  1258→```
  1259→Question:
  1260→    text            : String              -- the question to present to the human
  1261→    type            : QuestionType        -- determines the UI and valid answers
  1262→    options         : List<Option>        -- for MULTIPLE_CHOICE type
  1263→    default         : Answer or NONE      -- default if timeout/skip
  1264→    timeout_seconds : Float or NONE       -- max wait time
  1265→    stage           : String              -- originating stage name (for display)
  1266→    metadata        : Map<String, Any>    -- arbitrary key-value pairs
  1267→
  1268→QuestionType:
  1269→    YES_NO              -- yes/no binary choice
  1270→    MULTIPLE_CHOICE     -- select one from a list of options
  1271→    FREEFORM            -- free text input
  1272→    CONFIRMATION        -- yes/no confirmation (semantically distinct from YES_NO)
  1273→
  1274→Option:
  1275→    key   : String    -- accelerator key (e.g., "Y", "A")
  1276→    label : String    -- display text (e.g., "Yes, deploy to production")
  1277→```
  1278→
  1279→### 6.3 Answer Model
  1280→
  1281→```
  1282→Answer:
  1283→    value           : String or AnswerValue   -- the selected value
  1284→    selected_option : Option or NONE          -- the full selected option (for MULTIPLE_CHOICE)
  1285→    text            : String                  -- free text response (for FREEFORM)
  1286→
  1287→AnswerValue:
  1288→    YES       -- affirmative
  1289→    NO        -- negative
  1290→    SKIPPED   -- human skipped the question
  1291→    TIMEOUT   -- no response within timeout
  1292→```
  1293→
  1294→### 6.4 Built-In Interviewer Implementations
  1295→
  1296→**AutoApproveInterviewer:** Always selects YES for yes/no questions and the first option for multiple choice. Used for automated testing and CI/CD pipelines where no human is available.
  1297→
  1298→```
  1299→AutoApproveInterviewer:
  1300→    FUNCTION ask(question) -> Answer:
  1301→        IF question.type IN {YES_NO, CONFIRMATION}:
  1302→            RETURN Answer(value=YES)
  1303→        IF question.type == MULTIPLE_CHOICE AND question.options is not empty:
  1304→            RETURN Answer(value=question.options[0].key, selected_option=question.options[0])
  1305→        RETURN Answer(value="auto-approved", text="auto-approved")
  1306→```
  1307→
  1308→**ConsoleInterviewer (CLI):** Reads from standard input. Displays formatted prompts with option keys. Supports timeout via non-blocking read.
  1309→
  1310→```
  1311→ConsoleInterviewer:
  1312→    FUNCTION ask(question) -> Answer:
  1313→        print("[?] " + question.text)
  1314→        IF question.type == MULTIPLE_CHOICE:
  1315→            FOR EACH option IN question.options:
  1316→                print("  [" + option.key + "] " + option.label)
  1317→            response = read_input("Select: ")
  1318→            RETURN find_matching_option(response, question.options)
  1319→        IF question.type == YES_NO:
  1320→            response = read_input("[Y/N]: ")
  1321→            RETURN Answer(value=YES if response is "y" ELSE NO)
  1322→        IF question.type == FREEFORM:
  1323→            response = read_input("> ")
  1324→            RETURN Answer(text=response)
  1325→```
  1326→
  1327→**CallbackInterviewer:** Delegates question answering to a provided callback function. Useful for integrating with external systems (Slack, web UI, API).
  1328→
  1329→```
  1330→CallbackInterviewer:
  1331→    callback : Function(Question) -> Answer
  1332→
  1333→    FUNCTION ask(question) -> Answer:
  1334→        RETURN callback(question)
  1335→```
  1336→
  1337→**QueueInterviewer:** Reads answers from a pre-filled answer queue. Used for deterministic testing and replay.
  1338→
  1339→```
  1340→QueueInterviewer:
  1341→    answers : Queue<Answer>
  1342→
  1343→    FUNCTION ask(question) -> Answer:
  1344→        IF answers is not empty:
  1345→            RETURN answers.dequeue()
  1346→        RETURN Answer(value=SKIPPED)
  1347→```
  1348→
  1349→**RecordingInterviewer:** Wraps another interviewer and records all question-answer pairs. Used for replay, debugging, and audit trails.
  1350→
  1351→```
  1352→RecordingInterviewer:
  1353→    inner      : Interviewer
  1354→    recordings : List<(Question, Answer)>
  1355→
  1356→    FUNCTION ask(question) -> Answer:
  1357→        answer = inner.ask(question)
  1358→        recordings.append((question, answer))
  1359→        RETURN answer
  1360→```
  1361→
  1362→### 6.5 Timeout Handling
  1363→
  1364→If a human does not respond within the configured `timeout_seconds`:
  1365→
  1366→1. If the question has a `default` answer, use it.
  1367→2. If no default, return `Answer(value=TIMEOUT)`.
  1368→3. The handler decides how to handle a timeout (retry the question, fail, or proceed with assumptions).
  1369→
  1370→For `wait.human` nodes, the node attribute `human.default_choice` specifies which edge target to select on timeout.

  1374→## 7. Validation and Linting
  1375→
  1376→### 7.1 Diagnostic Model
  1377→
  1378→Validation produces a list of diagnostics, each with a severity level. The engine must refuse to execute a pipeline with error-severity diagnostics.
  1379→
  1380→```
  1381→Diagnostic:
  1382→    rule     : String                    -- rule identifier (e.g., "start_node")
  1383→    severity : Severity                  -- ERROR, WARNING, or INFO
  1384→    message  : String                    -- human-readable description
  1385→    node_id  : String                    -- related node ID (optional)
  1386→    edge     : (String, String) or NONE  -- related edge as (from, to) (optional)
  1387→    fix      : String                    -- suggested fix (optional)
  1388→
  1389→Severity:
  1390→    ERROR     -- pipeline will not execute
  1391→    WARNING   -- pipeline will execute but behavior may be unexpected
  1392→    INFO      -- informational note
  1393→```
  1394→
  1395→### 7.2 Built-In Lint Rules
  1396→
  1397→| Rule ID                  | Severity | Description |
  1398→|--------------------------|----------|-------------|
  1399→| `start_node`             | ERROR    | Pipeline must have exactly one start node (shape=Mdiamond or id matching `start`/`Start`). |
  1400→| `terminal_node`          | ERROR    | Pipeline must have at least one terminal node (shape=Msquare or id matching `exit`/`end`). |
  1401→| `reachability`           | ERROR    | All nodes must be reachable from the start node via BFS/DFS traversal. |
  1402→| `edge_target_exists`     | ERROR    | Every edge target must reference an existing node ID. |
  1403→| `start_no_incoming`      | ERROR    | The start node must have no incoming edges. |
  1404→| `exit_no_outgoing`       | ERROR    | The exit node must have no outgoing edges. |
  1405→| `condition_syntax`       | ERROR    | Edge condition expressions must parse correctly (valid operators and keys). |
  1406→| `stylesheet_syntax`      | ERROR    | The `model_stylesheet` attribute must parse as valid stylesheet rules. |
  1407→| `type_known`             | WARNING  | Node `type` values should be recognized by the handler registry. |
  1408→| `fidelity_valid`         | WARNING  | Fidelity mode values must be one of: `full`, `truncate`, `compact`, `summary:low`, `summary:medium`, `summary:high`. |
  1409→| `retry_target_exists`    | WARNING  | `retry_target` and `fallback_retry_target` must reference existing nodes. |
  1410→| `goal_gate_has_retry`    | WARNING  | Nodes with `goal_gate=true` should have a `retry_target` or `fallback_retry_target`. |
  1411→| `prompt_on_llm_nodes`    | WARNING  | Nodes that resolve to the codergen handler should have a `prompt` or `label` attribute. |
  1412→
  1413→### 7.3 Validation API
  1414→
  1415→```
  1416→FUNCTION validate(graph, extra_rules=NONE) -> List<Diagnostic>:
  1417→    rules = BUILT_IN_RULES
  1418→    IF extra_rules is not NONE:
  1419→        rules = rules + extra_rules
  1420→    diagnostics = []
  1421→    FOR EACH rule IN rules:
  1422→        diagnostics.extend(rule.apply(graph))
  1423→    RETURN diagnostics
  1424→
  1425→
  1426→FUNCTION validate_or_raise(graph, extra_rules=NONE):
  1427→    diagnostics = validate(graph, extra_rules)
  1428→    errors = [d FOR d IN diagnostics WHERE d.severity == ERROR]
  1429→    IF errors is not empty:
  1430→        RAISE ValidationError with error messages
  1431→    RETURN diagnostics
  1432→```
  1433→
  1434→### 7.4 Custom Lint Rules
  1435→
  1436→Implementations may register custom lint rules by implementing the rule interface:
  1437→
  1438→```
  1439→INTERFACE LintRule:
  1440→    name : String
  1441→    FUNCTION apply(graph) -> List<Diagnostic>
  1442→```
  1443→
  1444→Custom rules are appended to the built-in rules and run during validation.
  1445→

  1448→## 8. Model Stylesheet
  1449→
  1450→### 8.1 Overview
  1451→
  1452→The `model_stylesheet` graph attribute provides CSS-like rules for setting default LLM configuration on nodes. This centralizes model selection so that individual nodes do not need to specify `llm_model`, `llm_provider`, and `reasoning_effort` on every node.
  1453→
  1454→### 8.2 Stylesheet Grammar
  1455→
  1456→```
  1457→Stylesheet    ::= Rule+
  1458→Rule          ::= Selector '{' Declaration ( ';' Declaration )* ';'? '}'
  1459→Selector      ::= '*' | '#' Identifier | '.' ClassName
  1460→ClassName     ::= [a-z0-9-]+
  1461→Declaration   ::= Property ':' PropertyValue
  1462→Property      ::= 'llm_model' | 'llm_provider' | 'reasoning_effort'
  1463→PropertyValue ::= String | 'low' | 'medium' | 'high'
  1464→```
  1465→
  1466→### 8.3 Selectors and Specificity
  1467→
  1468→| Selector      | Matches                      | Specificity |
  1469→|---------------|------------------------------|-------------|
  1470→| `*`           | All nodes                    | 0 (lowest)  |
  1471→| `.class_name` | Nodes with that class        | 1 (medium)  |
  1472→| `#node_id`    | Specific node by ID          | 2 (highest) |
  1473→
  1474→Later rules of equal specificity override earlier ones. Explicit node attributes always override stylesheet values (highest precedence).
  1475→
  1476→### 8.4 Recognized Properties
  1477→
  1478→| Property           | Values                     | Description |
  1479→|--------------------|----------------------------|-------------|
  1480→| `llm_model`        | Any model identifier string | Provider-native model ID (e.g., `gpt-5.2`, `claude-opus-4-6`) |
  1481→| `llm_provider`     | Provider key string         | `openai`, `anthropic`, `gemini`, etc. |
  1482→| `reasoning_effort`  | `low`, `medium`, `high`    | Controls reasoning/thinking depth for the LLM |
  1483→
  1484→### 8.5 Application Order
  1485→
  1486→The resolution order for any model-related property on a node is:
  1487→
  1488→1. Explicit node attribute (e.g., `llm_model="gpt-5.2"` on the node) -- highest precedence
  1489→2. Stylesheet rule matching by specificity (ID > class > universal)
  1490→3. Graph-level default attribute
  1491→4. Handler/system default
  1492→
  1493→The stylesheet is applied as a transform after parsing and before validation. The transform walks all nodes and applies matching rules, but only sets properties that the node does not already have explicitly.
  1494→
  1495→### 8.6 Example
  1496→
  1497→```
  1498→digraph Pipeline {
  1499→    graph [
  1500→        goal="Implement feature X",
  1501→        model_stylesheet="
  1502→            * { llm_model: claude-sonnet-4-5; llm_provider: anthropic; }
  1503→            .code { llm_model: claude-opus-4-6; llm_provider: anthropic; }
  1504→            #critical_review { llm_model: gpt-5.2; llm_provider: openai; reasoning_effort: high; }
  1505→        "
  1506→    ]
  1507→
  1508→    start [shape=Mdiamond]
  1509→    exit  [shape=Msquare]
  1510→
  1511→    plan            [label="Plan", class="planning"]
  1512→    implement       [label="Implement", class="code"]
  1513→    critical_review [label="Critical Review", class="code"]
  1514→
  1515→    start -> plan -> implement -> critical_review -> exit
  1516→}
  1517→```
  1518→
  1519→In this example:
  1520→- `plan` gets `claude-sonnet-4-5` from the `*` rule (no class match for `.code`).
  1521→- `implement` gets `claude-opus-4-6` from the `.code` rule.
  1522→- `critical_review` gets `gpt-5.2` from the `#critical_review` rule (highest specificity), overriding the `.code` class match.
  1523→

  1526→## 9. Transforms and Extensibility
  1527→
  1528→### 9.1 AST Transforms
  1529→
  1530→Transforms are functions that modify the pipeline graph after parsing and before validation. They enable preprocessing, optimization, and structural rewriting without modifying the original DOT file.
  1531→
  1532→```
  1533→INTERFACE Transform:
  1534→    FUNCTION apply(graph) -> Graph
  1535→    -- Returns a new or modified graph. Should not modify the input graph.
  1536→```
  1537→
  1538→Transforms are applied in a defined order after parsing and before validation:
  1539→
  1540→```
  1541→FUNCTION prepare_pipeline(dot_source):
  1542→    graph = parse(dot_source)
  1543→    FOR EACH transform IN transforms:
  1544→        graph = transform.apply(graph)
  1545→    diagnostics = validate(graph)
  1546→    RETURN (graph, diagnostics)
  1547→```
  1548→
  1549→### 9.2 Built-In Transforms
  1550→
  1551→**Variable Expansion Transform:** Expands `$goal` in node `prompt` attributes to the graph-level `goal` attribute value.
  1552→
  1553→```
  1554→VariableExpansionTransform:
  1555→    FUNCTION apply(graph) -> Graph:
  1556→        FOR EACH node IN graph.nodes:
  1557→            IF node.prompt contains "$goal":
  1558→                node.prompt = replace(node.prompt, "$goal", graph.goal)
  1559→        RETURN graph
  1560→```
  1561→
  1562→**Stylesheet Application Transform:** Applies the `model_stylesheet` to resolve `llm_model`, `llm_provider`, and `reasoning_effort` for each node. See Section 8 for details.
  1563→
  1564→**Preamble Transform:** Synthesizes context carryover text for stages that do not use `full` fidelity. Applied at execution time (not at parse time) since it depends on runtime state.
  1565→
  1566→### 9.3 Custom Transforms
  1567→
  1568→Implementations may register custom transforms:
  1569→
  1570→```
  1571→runner.register_transform(MyCustomTransform())
  1572→```
  1573→
  1574→Custom transforms run after built-in transforms. Order of custom transforms follows registration order.
  1575→
  1576→**Use cases for custom transforms:**
  1577→- Inject logging or auditing nodes into the graph
  1578→- Add retry wrappers around certain node types
  1579→- Merge multiple graphs into a single pipeline
  1580→- Apply organization-specific defaults
  1581→
  1582→### 9.4 Pipeline Composition
  1583→
  1584→Attractor supports combining multiple DOT graphs through:
  1585→
  1586→**Sub-pipeline nodes:** A node whose handler runs an entire sub-graph as its execution. The manager loop handler (Section 4.11) is an example of this pattern.
  1587→
  1588→**Graph merging (via transform):** A custom transform can merge nodes and edges from one graph into another, enabling modular pipeline definitions.
  1589→
  1590→### 9.5 HTTP Server Mode
  1591→
  1592→Implementations may expose the pipeline engine as an HTTP service for web-based management, remote human interaction, and integration with external systems.
  1593→
  1594→**Core endpoints:**
  1595→
  1596→| Method | Path                                    | Description |
  1597→|--------|-----------------------------------------|-------------|
  1598→| `POST` | `/pipelines`                            | Submit a DOT source and start execution. Returns pipeline ID. |
  1599→| `GET`  | `/pipelines/{id}`                       | Get pipeline status and progress. |
  1600→| `GET`  | `/pipelines/{id}/events`                | SSE stream of pipeline events in real-time. |
  1601→| `POST` | `/pipelines/{id}/cancel`                | Cancel a running pipeline. |
  1602→| `GET`  | `/pipelines/{id}/graph`                 | Get rendered graph visualization (SVG). |
  1603→| `GET`  | `/pipelines/{id}/questions`             | Get pending human interaction questions. |
  1604→| `POST` | `/pipelines/{id}/questions/{qid}/answer`| Submit answer to a pending question. |
  1605→| `GET`  | `/pipelines/{id}/checkpoint`            | Get current checkpoint state. |
  1606→| `GET`  | `/pipelines/{id}/context`               | Get current context key-value store. |
  1607→
  1608→Human gates must be operable via web controls in addition to CLI. The server maintains SSE connections for real-time event streaming.
  1609→
  1610→### 9.6 Observability and Events
  1611→
  1612→The engine emits typed events during execution for UI, logging, and metrics integration:
  1613→
  1614→**Pipeline lifecycle events:**
  1615→- `PipelineStarted(name, id)` -- pipeline begins
  1616→- `PipelineCompleted(duration, artifact_count)` -- pipeline succeeded
  1617→- `PipelineFailed(error, duration)` -- pipeline failed
  1618→
  1619→**Stage lifecycle events:**
  1620→- `StageStarted(name, index)` -- stage begins
  1621→- `StageCompleted(name, index, duration)` -- stage succeeded
  1622→- `StageFailed(name, index, error, will_retry)` -- stage failed
  1623→- `StageRetrying(name, index, attempt, delay)` -- stage retrying
  1624→
  1625→**Parallel execution events:**
  1626→- `ParallelStarted(branch_count)` -- parallel block started
  1627→- `ParallelBranchStarted(branch, index)` -- branch started
  1628→- `ParallelBranchCompleted(branch, index, duration, success)` -- branch done
  1629→- `ParallelCompleted(duration, success_count, failure_count)` -- all branches done
  1630→
  1631→**Human interaction events:**
  1632→- `InterviewStarted(question, stage)` -- question presented
  1633→- `InterviewCompleted(question, answer, duration)` -- answer received
  1634→- `InterviewTimeout(question, stage, duration)` -- timeout reached
  1635→
  1636→**Checkpoint events:**
  1637→- `CheckpointSaved(node_id)` -- checkpoint written
  1638→
  1639→Events can be consumed via an observer/callback pattern or an asynchronous stream:
  1640→
  1641→```
  1642→-- Observer pattern
  1643→runner.on_event = FUNCTION(event):
  1644→    log(event.description)
  1645→
  1646→-- Stream pattern (for async runtimes)
  1647→FOR EACH event IN pipeline.events():
  1648→    process(event)
  1649→```
  1650→
  1651→### 9.7 Tool Call Hooks
  1652→
  1653→Graph-level or node-level attributes `tool_hooks.pre` and `tool_hooks.post` specify shell commands executed around each LLM tool call:
  1654→
  1655→- **Pre-hook:** Executed before every LLM tool call. Receives tool metadata via environment variables and stdin JSON. Exit code 0 means proceed; non-zero means skip the tool call.
  1656→- **Post-hook:** Executed after every LLM tool call. Receives tool metadata and result. Primarily for logging and auditing.
  1657→
  1658→Hook failures (non-zero exit) do not block the tool call but are recorded in the stage log.

  1662→## 10. Condition Expression Language
  1663→
  1664→### 10.1 Overview
  1665→
  1666→Edge conditions use a minimal boolean expression language to gate edge eligibility during routing. The language is deliberately simple to keep routing deterministic and inspectable.
  1667→
  1668→### 10.2 Grammar
  1669→
  1670→```
  1671→ConditionExpr  ::= Clause ( '&&' Clause )*
  1672→Clause         ::= Key Operator Literal
  1673→Key            ::= 'outcome'
  1674→                 | 'preferred_label'
  1675→                 | 'context.' Path
  1676→Path           ::= Identifier ( '.' Identifier )*
  1677→Operator       ::= '=' | '!='
  1678→Literal        ::= String | Integer | Boolean
  1679→```
  1680→
  1681→### 10.3 Semantics
  1682→
  1683→- Clauses are AND-combined, evaluated left to right.
  1684→- `outcome` refers to the executing node's outcome status (`success`, `retry`, `fail`, `partial_success`).
  1685→- `preferred_label` refers to the `preferred_label` value from the node's outcome.
  1686→- `context.*` keys look up values from the run context. Missing keys compare as empty strings (never equal to non-empty values).
  1687→- String comparison is exact and case-sensitive.
  1688→- All clauses must evaluate to true for the condition to pass.
  1689→
  1690→### 10.4 Variable Resolution
  1691→
  1692→```
  1693→FUNCTION resolve_key(key, outcome, context) -> String:
  1694→    IF key == "outcome":
  1695→        RETURN outcome.status as string
  1696→    IF key == "preferred_label":
  1697→        RETURN outcome.preferred_label
  1698→    IF key starts with "context.":
  1699→        value = context.get(key)
  1700→        IF value is not NONE:
  1701→            RETURN string(value)
  1702→        -- Also try without "context." prefix for convenience
  1703→        value = context.get(key without "context." prefix)
  1704→        IF value is not NONE:
  1705→            RETURN string(value)
  1706→        RETURN ""
  1707→    -- Direct context lookup for unqualified keys
  1708→    value = context.get(key)
  1709→    IF value is not NONE:
  1710→        RETURN string(value)
  1711→    RETURN ""
  1712→```
  1713→
  1714→### 10.5 Evaluation
  1715→
  1716→```
  1717→FUNCTION evaluate_condition(condition, outcome, context) -> Boolean:
  1718→    IF condition is empty:
  1719→        RETURN true  -- no condition means always eligible
  1720→
  1721→    clauses = split(condition, "&&")
  1722→    FOR EACH clause IN clauses:
  1723→        clause = trim(clause)
  1724→        IF clause is empty:
  1725→            CONTINUE
  1726→        IF NOT evaluate_clause(clause, outcome, context):
  1727→            RETURN false
  1728→    RETURN true
  1729→
  1730→
  1731→FUNCTION evaluate_clause(clause, outcome, context) -> Boolean:
  1732→    IF clause contains "!=":
  1733→        (key, value) = split(clause, "!=", max=1)
  1734→        RETURN resolve_key(trim(key), outcome, context) != trim(value)
  1735→    ELSE IF clause contains "=":
  1736→        (key, value) = split(clause, "=", max=1)
  1737→        RETURN resolve_key(trim(key), outcome, context) == trim(value)
  1738→    ELSE:
  1739→        -- Bare key: check if truthy
  1740→        RETURN bool(resolve_key(trim(clause), outcome, context))
  1741→```
  1742→
  1743→### 10.6 Examples
  1744→
  1745→```
  1746→-- Route on success
  1747→plan -> implement [condition="outcome=success"]
  1748→
  1749→-- Route on failure
  1750→plan -> fix [condition="outcome=fail"]
  1751→
  1752→-- Route on success AND a context flag
  1753→validate -> deploy [condition="outcome=success && context.tests_passed=true"]
  1754→
  1755→-- Route when a context value is not a specific value
  1756→review -> iterate [condition="context.loop_state!=exhausted"]
  1757→
  1758→-- Route based on preferred label
  1759→gate -> fix [condition="preferred_label=Fix"]
  1760→```
  1761→
  1762→### 10.7 Extended Operators (Future)
  1763→
  1764→The current condition language supports only `=` (equals) and `!=` (not equals) with AND (`&&`) conjunction. Future versions may add:
  1765→
  1766→- `contains` -- substring or set membership
  1767→- `matches` -- regular expression matching
  1768→- `OR` -- disjunction
  1769→- `NOT` -- negation
  1770→- `>`, `<`, `>=`, `<=` -- numeric comparison
  1771→
  1772→These are documented here as potential extensions. Implementations should not add them without updating the grammar and validation rules.

  1776→## 11. Definition of Done
  1777→
  1778→This section defines how to validate that an implementation of this spec is complete and correct. An implementation is done when every item is checked off.
  1779→
  1780→### 11.1 DOT Parsing
  1781→
  1782→- [ ] Parser accepts the supported DOT subset (digraph with graph/node/edge attribute blocks)
  1783→- [ ] Graph-level attributes (`goal`, `label`, `model_stylesheet`) are extracted correctly
  1784→- [ ] Node attributes are parsed including multi-line attribute blocks (attributes spanning multiple lines within `[...]`)
  1785→- [ ] Edge attributes (`label`, `condition`, `weight`) are parsed correctly
  1786→- [ ] Chained edges (`A -> B -> C`) produce individual edges for each pair
  1787→- [ ] Node/edge default blocks (`node [...]`, `edge [...]`) apply to subsequent declarations
  1788→- [ ] Subgraph blocks are flattened (contents kept, wrapper removed)
  1789→- [ ] `class` attribute on nodes merges in attributes from the stylesheet
  1790→- [ ] Quoted and unquoted attribute values both work
  1791→- [ ] Comments (`//` and `/* */`) are stripped before parsing
  1792→
  1793→### 11.2 Validation and Linting
  1794→
  1795→- [ ] Exactly one start node (shape=Mdiamond) is required
  1796→- [ ] Exactly one exit node (shape=Msquare) is required
  1797→- [ ] Start node has no incoming edges
  1798→- [ ] Exit node has no outgoing edges
  1799→- [ ] All nodes are reachable from start (no orphans)
  1800→- [ ] All edges reference valid node IDs
  1801→- [ ] Codergen nodes (shape=box) have non-empty `prompt` attribute (warning if missing)
  1802→- [ ] Condition expressions on edges parse without errors
  1803→- [ ] `validate_or_raise()` throws on error-severity violations
  1804→- [ ] Lint results include rule name, severity (error/warning), node/edge ID, and message
  1805→
  1806→### 11.3 Execution Engine
  1807→
  1808→- [ ] Engine resolves the start node and begins execution there
  1809→- [ ] Each node's handler is resolved via shape-to-handler-type mapping
  1810→- [ ] Handler is called with (node, context, graph, logs_root) and returns an Outcome
  1811→- [ ] Outcome is written to `{logs_root}/{node_id}/status.json`
  1812→- [ ] Edge selection follows the 5-step priority: condition match -> preferred label -> suggested IDs -> weight -> lexical
  1813→- [ ] Engine loops: execute node -> select edge -> advance to next node -> repeat
  1814→- [ ] Terminal node (shape=Msquare) stops execution
  1815→- [ ] Pipeline outcome is "success" if all goal_gate nodes succeeded, "fail" otherwise
  1816→
  1817→### 11.4 Goal Gate Enforcement
  1818→
  1819→- [ ] Nodes with `goal_gate=true` are tracked throughout execution
  1820→- [ ] Before allowing exit via a terminal node, the engine checks all goal gate nodes have status SUCCESS
  1821→- [ ] If any goal gate node has not succeeded, the engine routes to `retry_target` (if configured) instead of exiting
  1822→- [ ] If no retry_target and goal gates unsatisfied, pipeline outcome is "fail"
  1823→
  1824→### 11.5 Retry Logic
  1825→
  1826→- [ ] Nodes with `max_retries > 0` are retried on RETRY or FAIL outcomes
  1827→- [ ] Retry count is tracked per-node and respects the configured limit
  1828→- [ ] Backoff between retries works (constant, linear, or exponential as configured)
  1829→- [ ] Jitter is applied to backoff delays when configured
  1830→- [ ] After retry exhaustion, the node's final outcome is used for edge selection
  1831→
  1832→### 11.6 Node Handlers
  1833→
  1834→- [ ] **Start handler:** Returns SUCCESS immediately (no-op)
  1835→- [ ] **Exit handler:** Returns SUCCESS immediately (no-op, engine checks goal gates)
  1836→- [ ] **Codergen handler:** Expands `$goal` in prompt, calls `CodergenBackend.run()`, writes prompt.md and response.md to stage dir
  1837→- [ ] **Wait.human handler:** Presents outgoing edge labels as choices to the interviewer, returns selected label as preferred_label
  1838→- [ ] **Conditional handler:** Passes through; engine evaluates edge conditions against outcome/context
  1839→- [ ] **Parallel handler:** Fans out to multiple target nodes concurrently (or sequentially as fallback)
  1840→- [ ] **Fan-in handler:** Waits for all parallel branches to complete before proceeding
  1841→- [ ] **Tool handler:** Executes configured tool/command and returns result
  1842→- [ ] Custom handlers can be registered by type string
  1843→
  1844→### 11.7 State and Context
  1845→
  1846→- [ ] Context is a key-value store accessible to all handlers
  1847→- [ ] Handlers can read context and return `context_updates` in the Outcome
  1848→- [ ] Context updates are merged after each node execution
  1849→- [ ] Checkpoint is saved after each node completion (current_node, completed_nodes, context, retry counts)
  1850→- [ ] Resume from checkpoint: load checkpoint -> restore state -> continue from current_node
  1851→- [ ] Artifacts are written to `{logs_root}/{node_id}/` (prompt.md, response.md, status.json)
  1852→
  1853→### 11.8 Human-in-the-Loop
  1854→
  1855→- [ ] Interviewer interface works: `ask(question) -> Answer`
  1856→- [ ] Question supports types: SINGLE_SELECT, MULTI_SELECT, FREE_TEXT, CONFIRM
  1857→- [ ] AutoApproveInterviewer always selects the first option (for automation/testing)
  1858→- [ ] ConsoleInterviewer prompts in terminal and reads user input
  1859→- [ ] CallbackInterviewer delegates to a provided function
  1860→- [ ] QueueInterviewer reads from a pre-filled answer queue (for testing)
  1861→
  1862→### 11.9 Condition Expressions
  1863→
  1864→- [ ] `=` (equals) operator works for string comparison
  1865→- [ ] `!=` (not equals) operator works
  1866→- [ ] `&&` (AND) conjunction works with multiple clauses
  1867→- [ ] `outcome` variable resolves to the current node's outcome status
  1868→- [ ] `preferred_label` variable resolves to the outcome's preferred label
  1869→- [ ] `context.*` variables resolve to context values (missing keys = empty string)
  1870→- [ ] Empty condition always evaluates to true (unconditional edge)
  1871→
  1872→### 11.10 Model Stylesheet
  1873→
  1874→- [ ] Stylesheet is parsed from the graph's `model_stylesheet` attribute
  1875→- [ ] Selectors by shape name work (e.g., `box { model = "claude-opus-4-6" }`)
  1876→- [ ] Selectors by class name work (e.g., `.fast { model = "gemini-3-flash-preview" }`)
  1877→- [ ] Selectors by node ID work (e.g., `#review { reasoning_effort = "high" }`)
  1878→- [ ] Specificity order: universal < shape < class < ID
  1879→- [ ] Stylesheet properties are overridden by explicit node attributes
  1880→
  1881→### 11.11 Transforms and Extensibility
  1882→
  1883→- [ ] AST transforms can modify the Graph between parsing and validation
  1884→- [ ] Transform interface: `transform(graph) -> graph`
  1885→- [ ] Built-in variable expansion transform replaces `$goal` in prompts
  1886→- [ ] Custom transforms can be registered and run in order
  1887→- [ ] HTTP server mode (if implemented): POST /run starts pipeline, GET /status checks state, POST /answer submits human input
  1888→
  1889→### 11.12 Cross-Feature Parity Matrix
  1890→
  1891→Run this validation matrix -- each cell must pass:

  2046→## Appendix C: Status File Contract
  2047→
  2048→Each non-terminal node writes a `status.json` file in its stage directory. This file drives routing decisions and provides an audit trail.
  2049→
  2050→```
  2051→{
  2052→    "outcome": "success | retry | fail | partial_success",
  2053→    "preferred_next_label": "<edge label or empty>",
  2054→    "suggested_next_ids": ["<node_id>", ...],
  2055→    "context_updates": {
  2056→        "key": "value",
  2057→        "nested.key": "value"
  2058→    },
  2059→    "notes": "Human-readable execution summary"
  2060→}
  2061→```
  2062→
  2063→| Field                  | Type            | Required | Description |
  2064→|------------------------|-----------------|----------|-------------|
  2065→| `outcome`              | String (enum)   | Yes      | Outcome status. Drives routing and goal checks. |
  2066→| `preferred_next_label` | String          | No       | Edge label to prioritize for next transition. |
  2067→| `suggested_next_ids`   | List of Strings | No       | Fallback target node IDs if no label match. |
  2068→| `context_updates`      | Map             | No       | Key-value pairs merged into the run context. |
  2069→| `notes`                | String          | No       | Human-readable log entries. |
  2070→
  2071→When `auto_status=true` on a node and no `status.json` was written by the handler, the engine synthesizes: `{"outcome": "success", "notes": "auto-status: handler completed without writing status"}`.

  2075→## Appendix D: Error Categories
  2076→
  2077→Every error during pipeline execution falls into one of three categories:
  2078→
  2079→**Retryable errors** are transient failures where re-execution may succeed. Examples: LLM rate limits, network timeouts, temporary service unavailability. The engine retries these automatically per the node's retry policy.
  2080→
  2081→**Terminal errors** are permanent failures where re-execution will not help. Examples: invalid prompt, missing required context, authentication failures. The engine does not retry these; it immediately routes to the failure path.
  2082→
  2083→**Pipeline errors** are structural failures in the pipeline itself. Examples: no start node, unreachable nodes, invalid conditions. These are detected during validation (before execution) when possible. Runtime detection causes immediate pipeline termination.
