Overview and Goals\n    24→\n    25→### 1.1 Problem Statement\n    26→\n    27→A coding agent is a system that takes a natural language instruction (\"fix the login bug\", \"add dark mode\", \"write tests for this module\"), plans a solution, and executes it by reading files, editing code, running commands, and iterating until the task is done. The core challenge is orchestrating an agentic loop that coordinates LLM calls, tool execution, context management, and provider-specific behavior into a reliable autonomous workflow.\n    28→\n    29→Each LLM provider's models are trained and optimized for specific tool interfaces and system prompts. GPT-5.2 and the GPT-5.2-codex series work best with the same tools and prompts as codex-rs. Gemini models work best with the same tools and prompts as gemini-cli. Anthropic models work best with the same tools and prompts as Claude Code. A good coding agent respects this reality rather than forcing a universal toolset on all models.\n    30→\n    31→### 1.2 Why a Library, Not a CLI\n    32→\n    33→Tools like Claude Code, Codex CLI, and Gemini CLI exist as end-user CLIs. You can run them in non-interactive mode and pipe output, but that gives you a black box: text goes in, text comes out. You cannot programmatically inspect the conversation mid-run, inject steering messages between tool calls, swap the execution environment, change reasoning effort on the fly, observe individual tool calls as they happen, or compose agents into larger systems.\n    34→\n    35→This spec defines a **library** -- a programmable agentic loop that a host application controls at every step. The host can:\n    36→\n    37→- **Submit input and observe every event** as the agent thinks, calls tools, and produces output -- not after the fact, but in real time as it happens.\n    38→- **Steer the agent mid-task** by injecting messages between tool rounds, redirecting it without restarting.\n    39→- **Change configuration on the fly** -- reasoning effort, model, timeouts -- between any two turns.\n    40→- **Swap where tools run** by providing a different execution environment (local, Docker, Kubernetes, WASM, SSH) without changing any tool logic.\n    41→- **Compose agents** by spawning subagents for parallel work, each with their own history but sharing the same filesystem.\n    42→- **Build on top of it** -- CLIs, IDEs, web UIs, batch systems, CI pipelines, evaluation harnesses, and agent-to-agent coordination systems all consume the same library.\n    43→\n    44→The fidelity of control is the point. Every coding agent CLI is built on an agentic loop internally; this spec makes that loop a first-class, programmable interface.\n    45→\n    46→### 1.3 Design Principles\n    47→\n    48→**Programmable-first.** The agent is a library, not a CLI. Every aspect of the loop -- tool execution, event delivery, steering, configuration -- is accessible programmatically. A CLI is one possible host application, not the primary interface.\n    49→\n    50→**Provider-aligned.** Each model family works best with its native agent's tools and system prompts. The spec defines provider-specific tool profiles, not a single universal set. Start from the provider's native toolset and extend it.\n    51→\n    52→**Extensible execution.** Tool execution is abstracted behind an `ExecutionEnvironment` interface. The default runs locally. Implementations can target Docker, Kubernetes, WASM, or any remote host. Changing where tools run should not require changing the tools themselves.\n    53→\n    54→**Event-driven.** Every agent action emits a typed event for UI rendering, logging, and integration. The event stream is the primary interface for host applications.\n    55→\n    56→**Hackable.** Reasonable defaults with override points everywhere -- timeouts, output sizes, tool sets, execution environments, system prompts, reasoning effort. The spec prescribes defaults, not ceilings.\n    57→\n    58→**Language-agnostic.** All code is pseudocode. Data structures use neutral notation. No specific programming language is assumed.\n    59→\n    60→### 1.3 Architecture\n    61→\n    62→```\n    63→+--------------------------------------------------+\n    64→|  Host Application (CLI, IDE, Web UI)              |\n    65→+--------------------------------------------------+\n    66→        |                            ^\n    67→        | submit(input)              | events\n    68→        v                            |\n    69→+--------------------------------------------------+\n    70→|  Coding Agent Loop                                |\n    71→|  +--------------------+  +---------------------+ |\n    72→|  | Session            |  | Provider Profiles   | |\n    73→|  |  - history         |  |  - OpenAI (codex)   | |\n    74→|  |  - steering queue  |  |  - Anthropic (cc)   | |\n    75→|  |  - event emitter   |  |  - Gemini (cli)     | |\n    76→|  +--------------------+  +---------------------+ |\n    77→|  +--------------------+  +---------------------+ |\n    78→|  | Tool Registry      |  | Execution Env       | |\n    79→|  |  - tool dispatch   |  |  - local (default)  | |\n    80→|  |  - truncation      |  |  - docker           | |\n    81→|  |  - validation      |  |  - k8s / wasm / ssh | |\n    82→|  +--------------------+  +---------------------+ |\n    83→+--------------------------------------------------+\n    84→        |\n    85→        v\n    86→+--------------------------------------------------+\n    87→|  Unified LLM SDK (Client.complete / stream)       |\n    88→+--------------------------------------------------+\n    89→        |\n    90→        v\n    91→+--------------------------------------------------+\n    92→|  LLM Provider APIs                                |\n    93→|  (OpenAI Responses / Anthropic Messages / Gemini) |\n    94→+--------------------------------------------------+\n    95→```\n    96→\n    97→The agent loop does NOT use the Unified LLM SDK's `generate()` high-level function (which has its own tool loop). Agentic Loop\n   125→\n   126→### 2.1 Session\n   127→\n   128→The Session is the central orchestrator. It holds the conversation state, dispatches tool calls, manages the event stream, and enforces limits.\n   129→\n   130→```\n   131→RECORD Session:\n   132→    id                : String                  -- UUID, assigned at creation\n   133→    provider_profile  : ProviderProfile         -- tools + system prompt for the active model\n   134→    execution_env     : ExecutionEnvironment    -- where tools run\n   135→    history           : List<Turn>              -- ordered conversation turns\n   136→    event_emitter     : EventEmitter            -- delivers events to host application\n   137→    config            : SessionConfig           -- limits, timeouts, settings\n   138→    state             : SessionState            -- current lifecycle state\n   139→    llm_client        : Client                  -- from the Unified LLM SDK\n   140→    steering_queue    : Queue<String>           -- messages to inject between tool rounds\n   141→    followup_queue    : Queue<String>           -- messages to process after current input completes\n   142→    subagents         : Map<String, SubAgent>   -- active child agents\n   143→```\n   144→\n   145→### 2.2 Session Configuration\n   146→\n   147→```\n   148→RECORD SessionConfig:\n   149→    max_turns                   : Integer = 0       -- 0 = unlimited\n   150→    max_tool_rounds_per_input   : Integer = 0       -- 0 = unlimited, per user input, not per session\n   151→    default_command_timeout_ms  : Integer = 10000   -- 10 seconds\n   152→    max_command_timeout_ms      : Integer = 600000  -- 10 minutes\n   153→    reasoning_effort            : String | None     -- \"low\", \"medium\", \"high\", or null\n   154→    tool_output_limits          : Map<String, Integer>  -- per-tool char limits (see Section 5)\n   155→    enable_loop_detection       : Boolean = true\n   156→    loop_detection_window       : Integer = 10      -- consecutive identical calls before warning\n   157→    max_subagent_depth          : Integer = 1       -- max nesting level for subagents\n   158→```\n   159→\n   160→### 2.3 Session Lifecycle\n   161→\n   162→```\n   163→ENUM SessionState:\n   164→    IDLE              -- waiting for user input\n   165→    PROCESSING        -- running the agentic loop\n   166→    AWAITING_INPUT    -- model asked the user a question\n   167→    CLOSED            -- session terminated (normal or error)\n   168→```\n   169→\n   170→State transitions:\n   171→\n   172→```\n   173→IDLE -> PROCESSING          -- on submit()\n   174→PROCESSING -> PROCESSING    -- tool loop continues\n   175→PROCESSING -> AWAITING_INPUT -- model asks user a question (no tool calls, open-ended)\n   176→PROCESSING -> IDLE          -- natural completion or turn limit\n   177→PROCESSING -> CLOSED        -- unrecoverable error\n   178→IDLE -> CLOSED              -- explicit close()\n   179→any -> CLOSED               -- abort signal\n   180→AWAITING_INPUT -> PROCESSING -- user provides answer\n   181→```\n   182→\n   183→### 2.4 Turn Types\n   184→\n   185→A Turn is a single entry in the conversation history.\n   186→\n   187→```\n   188→RECORD UserTurn:\n   189→    content     : String\n   190→    timestamp   : Timestamp\n   191→\n   192→RECORD AssistantTurn:\n   193→    content     : String            -- text output\n   194→    tool_calls  : List<ToolCall>    -- tool invocations requested by the model\n   195→    reasoning   : String | None     -- thinking/reasoning text (if available)\n   196→    usage       : Usage             -- token counts for this turn\n   197→    response_id : String | None     -- provider response ID\n   198→    timestamp   : Timestamp\n   199→\n   200→RECORD ToolResultsTurn:\n   201→    results     : List<ToolResult>  -- one per tool call\n   202→    timestamp   : Timestamp\n   203→\n   204→RECORD SystemTurn:\n   205→    content     : String\n   206→    timestamp   : Timestamp\n   207→\n   208→RECORD SteeringTurn:\n   209→    content     : String            -- injected steering message\n   210→    timestamp   : Timestamp\n   211→```\n   212→\n   213→### 2.5 The Core Agentic Loop\n   214→\n   215→This is the centerpiece of the spec. The loop runs until the model produces a text-only response (no tool calls), a limit is hit, or an abort signal fires.\n   216→\n   217→```\n   218→FUNCTION process_input(session, user_input):\n   219→    session.state = PROCESSING\n   220→    session.history.APPEND(UserTurn(content = user_input))\n   221→    session.emit(USER_INPUT, content = user_input)\n   222→\n   223→    -- Drain any pending steering messages before the first LLM call\n   224→    drain_steering(session)\n   225→\n   226→    round_count = 0\n   227→\n   228→    LOOP:\n   229→        -- 1. Check limits\n   230→        IF session.config.max_tool_rounds_per_input > 0 AND round_count >= session.config.max_tool_rounds_per_input:\n   231→            session.emit(TURN_LIMIT, round = round_count)\n   232→            BREAK\n   233→\n   234→        IF session.config.max_turns > 0 AND count_turns(session) >= session.config.max_turns:\n   235→            session.emit(TURN_LIMIT, total_turns = count_turns(session))\n   236→            BREAK\n   237→\n   238→        IF session.abort_signaled:\n   239→            BREAK\n   240→\n   241→        -- 2. Build LLM request using provider profile\n   242→        system_prompt = session.provider_profile.build_system_prompt(\n   243→            environment = session.execution_env,\n   244→            project_docs = discover_project_docs(session.execution_env.working_directory())\n   245→        )\n   246→        messages = convert_history_to_messages(session.history)\n   247→        tool_defs = session.provider_profile.tools()\n   248→\n   249→        request = Request(\n   250→            model           = session.provider_profile.model,\n   251→            messages        = [Message.system(system_prompt)] + messages,\n   252→            tools           = tool_defs,\n   253→            tool_choice     = \"auto\",\n   254→            reasoning_effort = session.config.reasoning_effort,\n   255→            provider        = session.provider_profile.id,\n   256→            provider_options = session.provider_profile.provider_options()\n   257→        )\n   258→\n   259→        -- 3. Call LLM via Unified LLM SDK (single-shot, no SDK-level tool loop)\n   260→        response = session.llm_client.complete(request)\n   261→\n   262→        -- 4. Record assistant turn\n   263→        assistant_turn = AssistantTurn(\n   264→            content     = response.text,\n   265→            tool_calls  = response.tool_calls,\n   266→            reasoning   = response.reasoning,\n   267→            usage       = response.usage,\n   268→            response_id = response.id\n   269→        )\n   270→        session.history.APPEND(assistant_turn)\n   271→        session.emit(ASSISTANT_TEXT_END, text = response.text, reasoning = response.reasoning)\n   272→\n   273→        -- 5. If no tool calls, natural completion\n   274→        IF response.tool_calls IS EMPTY:\n   275→            BREAK\n   276→\n   277→        -- 6. Execute tool calls through the execution environment\n   278→        round_count += 1\n   279→        results = execute_tool_calls(session, response.tool_calls)\n   280→        session.history.APPEND(ToolResultsTurn(results = results))\n   281→\n   282→        -- 7. Drain steering messages injected during tool execution\n   283→        drain_steering(session)\n   284→\n   285→        -- 8. Loop detection\n   286→        IF session.config.enable_loop_detection:\n   287→            IF detect_loop(session.history, session.config.loop_detection_window):\n   288→                warning = \"Loop detected: the last \" + session.config.loop_detection_window\n   289→                        + \" tool calls follow a repeating pattern. Try a different approach.\"\n   290→                session.history.APPEND(SteeringTurn(content = warning))\n   291→                session.emit(LOOP_DETECTION, message = warning)\n   292→\n   293→    END LOOP\n   294→\n   295→    -- Process follow-up messages if any are queued\n   296→    IF session.followup_queue IS NOT EMPTY:\n   297→        next_input = session.followup_queue.DEQUEUE()\n   298→        process_input(session, next_input)\n   299→        RETURN\n   300→\n   301→    session.state = IDLE\n   302→    session.emit(SESSION_END)\n   303→\n   304→\n   305→FUNCTION drain_steering(session):\n   306→    WHILE session.steering_queue IS NOT EMPTY:\n   307→        msg = session.steering_queue.DEQUEUE()\n   308→        session.history.APPEND(SteeringTurn(content = msg))\n   309→        session.emit(STEERING_INJECTED, content = msg)\n   310→\n   311→\n   312→FUNCTION execute_tool_calls(session, tool_calls):\n   313→    results = []\n   314→\n   315→    -- Execute tool calls (concurrently if profile supports parallel execution)\n   316→    IF session.provider_profile.supports_parallel_tool_calls AND LENGTH(tool_calls) > 1:\n   317→        results = AWAIT_ALL([\n   318→            execute_single_tool(session, tc) FOR tc IN tool_calls\n   319→        ])\n   320→    ELSE:\n   321→        FOR EACH tc IN tool_calls:\n   322→            result = execute_single_tool(session, tc)\n   323→            results.APPEND(result)\n   324→    RETURN results\n   325→\n   326→\n   327→FUNCTION execute_single_tool(session, tool_call):\n   328→    session.emit(TOOL_CALL_START, tool_name = tool_call.name, call_id = tool_call.id)\n   329→\n   330→    -- Look up tool in registry\n   331→    registered = session.provider_profile.tool_registry.get(tool_call.name)\n   332→    IF registered IS None:\n   333→        error_msg = \"Unknown tool: \" + tool_call.name\n   334→        session.emit(TOOL_CALL_END, call_id = tool_call.id, error = error_msg)\n   335→        RETURN ToolResult(tool_call_id = tool_call.id, content = error_msg, is_error = true)\n   336→\n   337→    -- Execute via execution environment\n   338→    TRY:\n   339→        raw_output = registered.execute(tool_call.arguments, session.execution_env)\n   340→\n   341→        -- Truncate output before sending to LLM (character-based first, then line-based)\n   342→        truncated_output = truncate_tool_output(raw_output, tool_call.name, session.config)\n   343→\n   344→        -- Emit full output via event stream (not truncated)\n   345→        session.emit(TOOL_CALL_END, call_id = tool_call.id, output = raw_output)\n   346→\n   347→        RETURN ToolResult(\n   348→            tool_call_id = tool_call.id,\n   349→            content = truncated_output,\n   350→            is_error = false\n   351→        )\n   352→\n   353→    CATCH error:\n   354→        error_msg = \"Tool error (\" + tool_call.name + \"): \" + str(error)\n   355→        session.emit(TOOL_CALL_END, call_id = tool_call.id, error = error_msg)\n   356→        RETURN ToolResult(tool_call_id = tool_call.id, content = error_msg, is_error = true)\n   357→```\n   358→\n   359→### 2.6 Steering\n   360→\n   361→Steering allows the host application to inject messages into the conversation between tool rounds. This is how a user can redirect the agent mid-task without waiting for it to finish.\n   362→\n   363→```\n   364→session.steer(message: String)\n   365→    -- Queue a message to be injected after the current tool round completes.\n   366→    -- The message becomes a SteeringTurn in the history, converted to a\n   367→    -- user message for the LLM on the next call.\n   368→    -- If the agent is idle, the message is delivered on the next submit().\n   369→\n   370→session.follow_up(message: String)\n   371→    -- Queue a message to be processed after the current input is fully handled\n   372→    -- (model has produced a text-only response). Triggers a new processing cycle.\n   373→```\n   374→\n   375→SteeringTurns are converted to user-role messages when building the LLM request. This means the model sees them as additional user instructions.\n   376→\n   377→### 2.7 Reasoning Effort\n   378→\n   379→The `reasoning_effort` config controls how much reasoning/thinking the model does. It maps directly to the Unified LLM SDK's `reasoning_effort` field on the Request.\n   380→\n   381→| Value    | Effect                                                           |\n   382→|----------|------------------------------------------------------------------|\n   383→| \"low\"    | Minimal reasoning. Faster, cheaper. Good for simple tasks.      |\n   384→| \"medium\" | Balanced reasoning. Default for most tasks.                     |\n   385→| \"high\"   | Deep reasoning. Slower, more expensive. Good for complex tasks. |\n   386→| null     | Provider default (no override).                                 |\n   387→\n   388→Changing `reasoning_effort` mid-session takes effect on the next LLM call. For OpenAI reasoning models (GPT-5.2 series), this controls the reasoning token budget. For Anthropic models with extended thinking, this maps to the thinking budget. For Gemini models with thinking, this maps to thinkingConfig.\n   389→\n   390→### 2.8 Stop Conditions\n   391→\n   392→The loop exits when any of these conditions is met:\n   393→\n   394→1. **Natural completion.** The model responds with text only (no tool calls). The model is done.\n   395→2. **Round limit.** `max_tool_rounds_per_input` is reached. The agent stops and returns what it has.\n   396→3. **Turn limit.** `max_turns` across the entire session is reached.\n   397→4. **Abort signal.** The host application signals cancellation. The current LLM stream is closed, running processes are killed, and the session transitions to CLOSED.\n   398→5. **Unrecoverable error.** An authentication error, context overflow, or other non-retryable error. The session transitions to CLOSED.\n   399→\n   400→### 2.9 Event System\n   401→\n   402→Every agent action emits a typed event. Events are delivered via an async iterator (or language-appropriate equivalent) to the host application.\n   403→\n   404→```\n   405→RECORD SessionEvent:\n   406→    kind        : EventKind\n   407→    timestamp   : Timestamp\n   408→    session_id  : String\n   409→    data        : Map<String, Any>\n   410→\n   411→ENUM EventKind:\n   412→    SESSION_START           -- session created\n   413→    SESSION_END             -- session closed (includes final state)\n   414→    USER_INPUT              -- user submitted input\n   415→    ASSISTANT_TEXT_START     -- model began generating text\n   416→    ASSISTANT_TEXT_DELTA     -- incremental text token\n   417→    ASSISTANT_TEXT_END       -- model finished text (includes full text)\n   418→    TOOL_CALL_START         -- tool execution began (includes tool name, call ID)\n   419→    TOOL_CALL_OUTPUT_DELTA  -- incremental tool output (for streaming tools)\n   420→    TOOL_CALL_END           -- tool execution finished (includes FULL untruncated output)\n   421→    STEERING_INJECTED       -- a steering message was added to history\n   422→    TURN_LIMIT              -- a turn limit was hit\n   423→    LOOP_DETECTION          -- a loop pattern was detected\n   424→    ERROR                   -- an error occurred\n   425→```\n   426→\n   427→**Key design decision:** The `TOOL_CALL_END` event carries the FULL untruncated tool output. The LLM receives the truncated version. This means the host application (UI, logs) always has access to complete output even though the model sees an abbreviated version.\n   428→\n   429→### 2.10 Loop Detection\n   430→\n   431→Track the signature of each tool call (name + arguments hash). If the last N calls (default: 10) contain a repeating pattern (e.g., the same 2-3 calls cycling), inject a warning as a SteeringTurn telling the model to try a different approach.\n   432→\n   433→```\n   434→FUNCTION detect_loop(history, window_size) -> Boolean:\n   435→    recent_calls = extract_tool_call_signatures(history, last = window_size)\n   436→    IF LENGTH(recent_calls) < window_size: RETURN false\n   437→\n   438→    -- Check for repeating patterns of length 1, 2, or 3\n   439→    FOR pattern_len IN [1, 2, 3]:\n   440→        IF window_size % pattern_len != 0: CONTINUE\n   441→        pattern = recent_calls[0..pattern_len]\n   442→        all_match = true\n   443→        FOR i FROM pattern_len TO window_size STEP pattern_len:\n   444→            IF recent_calls[i..i+pattern_len] != pattern:\n   445→                all_match = false\n   446→                BREAK\n   447→        IF all_match: RETURN true\n   448→\n   449→    RETURN false\n   450→```\n   451→\n   452→---\n   453→\n   454→## 3. Provider-Aligned Toolsets\n   455→\n   456→### 3.1 The Provider Alignment Principle\n   457→\n   458→Models are trained and optimized for specific tool interfaces. OpenAI's models are trained on codex-rs's apply_patch format and tool schemas. Anthropic's models are trained on Claude Code's old_string/new_string editing and tool schemas. Gemini models are trained on gemini-cli's tool set.\n   459→\n   460→Using a provider's native tool format produces better results than forcing a universal format. **The initial base for each provider should be a 1:1 copy of the provider's reference agent -- the exact same system prompt, the exact same tool definitions, byte for byte.** Not a similar prompt. Not similar tools. The actual prompt and harness that the model was evaluated and optimized against. Then extend it with additional capabilities (like subagents). Do not make all providers conform to a single tool interface.\n   461→\n   462→### 3.2 ProviderProfile Interface\n   463→\n   464→```\n   465→INTERFACE ProviderProfile:\n   466→    id              : String            -- \"openai\", \"anthropic\", \"gemini\"\n   467→    model           : String            -- model identifier (e.g., \"gpt-5.2-codex\")\n   468→    tool_registry   : ToolRegistry      -- all tools available to this profile\n   469→\n   470→    FUNCTION build_system_prompt(environment, project_docs) -> String\n   471→    FUNCTION tools() -> List<ToolDefinition>\n   472→    FUNCTION provider_options() -> Map | None\n   473→\n   474→    -- Capability flags\n   475→    supports_reasoning           : Boolean\n   476→    supports_streaming           : Boolean\n   477→    supports_parallel_tool_calls : Boolean\n   478→    context_window_size          : Integer\n   479→```\n   480→\n   481→### 3.3 Shared Core Tools\n   482→\n   483→All profiles include these base tools. The parameter schemas and output formats may vary between profiles (to match the provider's native conventions), but the functionality is the same.\n   484→\n   485→#### read_file\n   486→\n   487→Reads a file's contents with line numbers.\n   488→\n   489→```\n   490→TOOL read_file:\n   491→    description: \"Read a file from the filesystem. Returns line-numbered content.\"\n   492→    parameters:\n   493→        file_path   : String (required)     -- absolute path to the file\n   494→        offset      : Integer (optional)    -- 1-based line number to start reading from\n   495→        limit       : Integer (optional)    -- max lines to read (default: 2000)\n   496→    returns: Line-numbered text content in \"NNN | content\" format\n   497→    errors: File not found, permission denied, binary file\n   498→```\n   499→\n   500→Behavior: Read the file, prepend line numbers, respect offset/limit. For image files, return the image data for multimodal models. For very large files without offset/limit, the tool output will be truncated by the truncation layer (Section 5).\n   501→\n   502→#### write_file\n   503→\n   504→Writes content to a file, creating it if it does not exist.\n   505→\n   506→```\n   507→TOOL write_file:\n   508→    description: \"Write content to a file. Creates the file and parent directories if needed.\"\n   509→    parameters:\n   510→        file_path   : String (required)     -- absolute path\n   511→        content     : String (required)     -- the full file content\n   512→    returns: Confirmation message with bytes written\n   513→    errors: Permission denied, disk full\n   514→```\n   515→\n   516→#### edit_file\n   517→\n   518→Searches for an exact string in a file and replaces it. This is the native editing format for Anthropic models.\n   519→\n   520→```\n   521→TOOL edit_file:\n   522→    description: \"Replace an exact string occurrence in a file.\"\n   523→    parameters:\n   524→        file_path   : String (required)\n   525→        old_string  : String (required)     -- exact text to find\n   526→        new_string  : String (required)     -- replacement text\n   527→        replace_all : Boolean (optional)    -- replace all occurrences (default: false)\n   528→    returns: Confirmation with number of replacements made\n   529→    errors: File not found, old_string not found, old_string not unique (when replace_all=false)\n   530→```\n   531→\n   532→Behavior: Exact string match. If `old_string` is not found exactly, the implementation may attempt fuzzy matching (whitespace normalization, Unicode equivalence) and report the match. If `old_string` matches multiple locations and `replace_all` is false, return an error asking the model to provide more context.\n   533→\n   534→#### shell\n   535→\n   536→Executes a command in the system shell.\n   537→\n   538→```\n   539→TOOL shell:\n   540→    description: \"Execute a shell command. Returns stdout, stderr, and exit code.\"\n   541→    parameters:\n   542→        command     : String (required)     -- the command to run\n   543→        timeout_ms  : Integer (optional)    -- override default timeout\n   544→        description : String (optional)     -- human-readable description of what this does\n   545→    returns: Command output (stdout + stderr), exit code, duration\n   546→    errors: Timeout, permission denied, command not found\n   547→```\n   548→\n   549→Behavior: Run in a new process group. Enforce timeout (default from SessionConfig, overridable per-call). On timeout: SIGTERM, wait 2 seconds, SIGKILL. Return collected output plus timeout message. Environment variable filtering applied (see Section 4).\n   550→\n   551→#### grep\n   552→\n   553→Searches file contents by pattern.\n   554→\n   555→```\n   556→TOOL grep:\n   557→    description: \"Search file contents using regex patterns.\"\n   558→    parameters:\n   559→        pattern         : String (required)     -- regex pattern\n   560→        path            : String (optional)     -- directory or file to search (default: working dir)\n   561→        glob_filter     : String (optional)     -- file pattern filter (e.g., \"*.py\")\n   562→        case_insensitive: Boolean (optional)    -- default: false\n   563→        max_results     : Integer (optional)    -- default: 100\n   564→    returns: Matching lines with file paths and line numbers\n   565→    errors: Invalid regex, path not found\n   566→```\n   567→\n   568→#### glob\n   569→\n   570→Finds files by name pattern.\n   571→\n   572→```\n   573→TOOL glob:\n   574→    description: \"Find files matching a glob pattern.\"\n   575→    parameters:\n   576→        pattern     : String (required)     -- glob pattern (e.g., \"**/*.ts\")\n   577→        path        : String (optional)     -- base directory (default: working dir)\n   578→    returns: List of matching file paths, sorted by modification time (newest first)\n   579→    errors: Invalid pattern, path not found\n   580→```\n   581→\n   582→### 3.4 OpenAI Profile (codex-rs-aligned)\n   583→\n   584→For GPT-5.2, GPT-5.2-codex, and other OpenAI models. Mirrors the codex-rs toolset.\n   585→\n   586→**Key difference: `apply_patch` replaces `edit_file` and `write_file` for file modifications.** OpenAI models are specifically trained on this format and produce significantly better edits when using it.\n   587→\n   588→Additional/modified tools beyond the shared core:\n   589→\n   590→#### apply_patch (OpenAI-specific)\n   591→\n   592→```\n   593→TOOL apply_patch:\n   594→    description: \"Apply code changes using the patch format. Supports creating, deleting,\n   595→                  and modifying files in a single operation.\"\n   596→    parameters:\n   597→        patch       : String (required)     -- the patch content in v4a format\n   598→    returns: List of affected file paths and operations performed\n   599→    errors: Parse error, file not found (for updates), verification failure\n   600→```\n   601→\n   602→The patch format is defined in full in [Appendix A](#appendix-a-apply_patch-v4a-format-reference).\n   603→\n   604→**Profile tool list for OpenAI:**\n   605→- `read_file` (same as shared core, maps to codex-rs `read_file`)\n   606→- `apply_patch` (replaces `edit_file` and `write_file` for modifications)\n   607→- `write_file` (kept for creating new files without patch overhead)\n   608→- `shell` (maps to codex-rs `exec_command`, 10s default timeout)\n   609→- `grep` (maps to codex-rs `grep_files`)\n   610→- `glob` (maps to codex-rs `list_dir`)\n   611→- `spawn_agent`, `send_input`, `wait`, `close_agent` (subagent tools, Section 7)\n   612→\n   613→**System prompt:** Should mirror the codex-rs system prompt structure. Cover identity, tool usage guidelines, the apply_patch format expectations, and coding best practices.\n   614→\n   615→**Provider options:** The OpenAI profile should set `reasoning.effort` on the Responses API request when `reasoning_effort` is configured.\n   616→\n   617→### 3.5 Anthropic Profile (Claude Code-aligned)\n   618→\n   619→For Claude Opus 4.6, Opus 4.5, Sonnet 4.5, Haiku 4.5, and older Claude models. Mirrors the Claude Code toolset.\n   620→\n   621→**Key difference: `edit_file` with `old_string`/`new_string` is the native editing format.** Anthropic models are specifically trained on this exact-match search-and-replace pattern. Do NOT use apply_patch with Anthropic models.\n   622→\n   623→**Profile tool list for Anthropic:**\n   624→- `read_file` (line-numbered output, offset/limit support)\n   625→- `write_file` (full file writes)\n   626→- `edit_file` (old_string/new_string -- this is the native format)\n   627→- `shell` (bash execution, 120s default timeout per Claude Code convention)\n   628→- `grep` (ripgrep-backed with output modes: content, files_with_matches, count)\n   629→- `glob` (file pattern matching sorted by mtime)\n   630→- Subagent tools (maps to Claude Code's Task tool pattern, Section 7)\n   631→\n   632→**System prompt:** Should mirror the Claude Code system prompt structure. Cover identity, tool selection guidance, the edit_file format (explain that `old_string` must be unique), file operation preferences (edit existing files over creating new ones), and coding best practices.\n   633→\n   634→**Provider options:** The Anthropic profile should pass beta headers (e.g., for extended thinking, 1M context) via `provider_options.anthropic.beta_headers`.\n   635→\n   636→### 3.6 Gemini Profile (gemini-cli-aligned)\n   637→\n   638→For Gemini 3 Flash, Gemini 2.5 Pro/Flash, and other Gemini models. Mirrors the gemini-cli toolset.\n   639→\n   640→**Profile tool list for Gemini:**\n   641→- `read_file` / `read_many_files` (batch reading support)\n   642→- `write_file`\n   643→- `edit_file` (search-and-replace style, matching gemini-cli conventions)\n   644→- `shell` (command execution, 10s default timeout)\n   645→- `grep` (ripgrep semantics)\n   646→- `glob` (file pattern matching)\n   647→- `list_dir` (directory listing with depth options)\n   648→- `web_search` (optional -- Gemini models have native grounding capabilities)\n   649→- `web_fetch` (optional -- fetch and extract content from URLs)\n   650→- Subagent tools (Section 7)\n   651→\n   652→**System prompt:** Should mirror the gemini-cli system prompt structure. Cover identity, tool usage, GEMINI.md conventions, and coding best practices.\n   653→\n   654→**Provider options:** Gemini profile should configure safety settings and grounding via `provider_options.gemini`.\n   655→\n   656→### 3.7 Extending Profiles with Custom Tools\n   657→\n   658→After a provider profile is loaded, additional tools can be registered:\n   659→\n   660→```\n   661→profile = create_openai_profile(model = \"gpt-5.2-codex\")\n   662→\n   663→-- Add a custom tool on top of the profile\n   664→profile.tool_registry.register(RegisteredTool(\n   665→    definition = ToolDefinition(\n   666→        name = \"run_tests\",\n   667→        description = \"Run the project's test suite\",\n   668→        parameters = { \"type\": \"object\", \"properties\": { \"filter\": { \"type\": \"string\" } } }\n   669→    ),\n   670→    executor = run_tests_function\n   671→))\n   672→```\n   673→\n   674→Name collisions are resolved by latest-wins: a custom tool with the same name as a profile tool overrides it.\n   675→\n   676→### 3.8 Tool Registry\n   677→\n   678→```\n   679→RECORD ToolDefinition:\n   680→    name        : String            -- unique identifier\n   681→    description : String            -- for the LLM\n   682→    parameters  : Dict              -- JSON Schema (root must be \"object\")\n   683→\n   684→RECORD RegisteredTool:\n   685→    definition  : ToolDefinition\n   686→    executor    : Function          -- (arguments, execution_env) -> String\n   687→\n   688→RECORD ToolRegistry:\n   689→    _tools      : Map<String, RegisteredTool>\n   690→\n   691→    register(tool)                  -- add or replace a tool\n   692→    unregister(name)                -- remove a tool\n   693→    get(name) -> RegisteredTool | None\n   694→    definitions() -> List<ToolDefinition>\n   695→    names() -> List<String>\n   696→```\n   697→\n   698→**Tool execution pipeline:**\n   699→\n   700→```\n   701→1. LOOKUP      -- find the RegisteredTool by name\n   702→2. VALIDATE    -- parse and validate arguments against JSON Schema\n   703→3. EXECUTE     -- call executor with (arguments, execution_env)\n   704→4. TRUNCATE    -- apply output size limits (Section 5)\n   705→5. EMIT        -- emit TOOL_CALL_END event with full output\n   706→6. RETURN      -- return truncated output as ToolResult\n   707→```\n   708→\n   709→---\n   710→\n   711→## 4. Tool Execution Environment\n   712→\n   713→### 4.1 The Execution Environment Abstraction\n   714→\n   715→All tool operations pass through an `ExecutionEnvironment` interface. This decouples tool logic from where it runs. The default runs locally. Swap in a different implementation to run the same tools in Docker, on a Kubernetes pod, over SSH, or in WASM.\n   716→\n   717→```\n   718→INTERFACE ExecutionEnvironment:\n   719→    -- File operations\n   720→    read_file(path: String, offset: Integer | None, limit: Integer | None) -> String\n   721→    write_file(path: String, content: String) -> void\n   722→    file_exists(path: String) -> Boolean\n   723→    list_directory(path: String, depth: Integer) -> List<DirEntry>\n   724→\n   725→    -- Command execution\n   726→    exec_command(\n   727→        command     : String,\n   728→        timeout_ms  : Integer,\n   729→        working_dir : String | None,\n   730→        env_vars    : Map<String, String> | None\n   731→    ) -> ExecResult\n   732→\n   733→    -- Search operations\n   734→    grep(pattern: String, path: String, options: GrepOptions) -> String\n   735→    glob(pattern: String, path: String) -> List<String>\n   736→\n   737→    -- Lifecycle\n   738→    initialize() -> void\n   739→    cleanup() -> void\n   740→\n   741→    -- Metadata\n   742→    working_directory() -> String\n   743→    platform() -> String           -- \"darwin\", \"linux\", \"windows\", \"wasm\"\n   744→    os_version() -> String\n   745→\n   746→RECORD ExecResult:\n   747→    stdout      : String\n   748→    stderr      : String\n   749→    exit_code   : Integer\n   750→    timed_out   : Boolean\n   751→    duration_ms : Integer\n   752→\n   753→RECORD DirEntry:\n   754→    name        : String\n   755→    is_dir      : Boolean\n   756→    size        : Integer | None\n   757→```\n   758→\n   759→### 4.2 LocalExecutionEnvironment (Required Implementation)\n   760→\n   761→The default. Runs everything on the local machine.\n   762→\n   763→**File operations:** Direct filesystem access. Paths are resolved relative to `working_directory()`.\n   764→\n   765→**Command execution:**\n   766→- Spawn in a new process group for clean killability\n   767→- Use the platform's default shell (`/bin/bash -c` on Linux/macOS, `cmd.exe /c` on Windows)\n   768→- Enforce timeout: on timeout, send SIGTERM to the process group, wait 2 seconds, then SIGKILL\n   769→- Capture stdout and stderr separately, then combine for the result\n   770→- Record wall-clock duration\n   771→\n   772→**Environment variable filtering:**\n   773→- By default, exclude variables matching: `*_API_KEY`, `*_SECRET`, `*_TOKEN`, `*_PASSWORD`, `*_CREDENTIAL` (case-insensitive)\n   774→- Always include: `PATH`, `HOME`, `USER`, `SHELL`, `LANG`, `TERM`, `TMPDIR`, language-specific paths (`GOPATH`, `CARGO_HOME`, `NVM_DIR`, etc.)\n   775→- Customizable via an env var policy: inherit all, inherit none (start clean), or inherit core only\n   776→\n   777→**Search operations:** Use `ripgrep` for grep if available, fall back to language-native regex search. Use filesystem globbing for glob.\n   778→\n   779→### 4.3 Alternative Environments (Extension Points)\n   780→\n   781→These are not required implementations. They demonstrate the extensibility of the interface.\n   782→\n   783→**DockerExecutionEnvironment:**\n   784→```\n   785→-- Commands execute inside a Docker container\n   786→exec_command(cmd, ...) -> docker exec <container_id> sh -c <cmd>\n   787→-- File operations use volume mounts or docker cp\n   788→read_file(path) -> docker cp <container_id>:<path> - | read\n   789→write_file(path, content) -> pipe content | docker cp - <container_id>:<path>\n   790→```\n   791→\n   792→**KubernetesExecutionEnvironment:**\n   793→```\n   794→-- Commands execute in a Kubernetes pod\n   795→exec_command(cmd, ...) -> kubectl exec <pod> -- sh -c <cmd>\n   796→-- File operations use kubectl cp\n   797→read_file(path) -> kubectl cp <pod>:<path> /dev/stdout\n   798→```\n   799→\n   800→**WASMExecutionEnvironment:**\n   801→```\n   802→-- For in-browser or embedded use\n   803→-- File operations use an in-memory filesystem (e.g., memfs)\n   804→-- Command execution is limited or emulated via WASI\n   805→```\n   806→\n   807→**RemoteSSHExecutionEnvironment:**\n   808→```\n   809→-- Commands execute over SSH\n   810→exec_command(cmd, ...) -> ssh <host> <cmd>\n   811→-- File operations use SCP/SFTP\n   812→read_file(path) -> sftp get <host>:<path>\n   813→```\n   814→\n   815→### 4.4 Composing Environments\n   816→\n   817→Execution environments can be wrapped for cross-cutting concerns:\n   818→\n   819→```\n   820→-- Logging wrapper\n   821→LoggingExecutionEnvironment(inner: ExecutionEnvironment):\n   822→    exec_command(cmd, ...):\n   823→        LOG(\"exec: \" + cmd)\n   824→        result = inner.exec_command(cmd, ...)\n   825→        LOG(\"exit: \" + result.exit_code + \" in \" + result.duration_ms + \"ms\")\n   826→        RETURN result\n   827→\n   828→-- Read-only wrapper (rejects all writes)\n   829→ReadOnlyExecutionEnvironment(inner: ExecutionEnvironment):\n   830→    write_file(path, content):\n   831→        RAISE \"Write operations are disabled in read-only mode\"\n   832→    exec_command(cmd, ...):\n   833→        -- Could analyze command for write intent, or allow all\n   834→        RETURN inner.exec_command(cmd, ...)\n   835→```\n   836→\n   837→---\n   838→\n   839→## 5. Tool Output and Context Management\n   840→\n   841→### 5.1 Tool Output Truncation\n   842→\n   843→When tool output exceeds the configured limit, it MUST be truncated before being sent to the LLM. The full output is always available via the event stream (`TOOL_CALL_END` event).\n   844→\n   845→**Truncation algorithm (head/tail split):**\n   846→\n   847→```\n   848→FUNCTION truncate_output(output: String, max_chars: Integer, mode: String) -> String:\n   849→    IF LENGTH(output) <= max_chars:\n   850→        RETURN output\n   851→\n   852→    IF mode == \"head_tail\":\n   853→        half = max_chars / 2\n   854→        removed = LENGTH(output) - max_chars\n   855→        RETURN output[0..half]\n   856→             + \"\\n\\n[WARNING: Tool output was truncated. \"\n   857→             + removed + \" characters were removed from the middle. \"\n   858→             + \"The full output is available in the event stream. \"\n   859→             + \"If you need to see specific parts, re-run the tool with more targeted parameters.]\\n\\n\"\n   860→             + output[-half..]\n   861→\n   862→    IF mode == \"tail\":\n   863→        removed = LENGTH(output) - max_chars\n   864→        RETURN \"[WARNING: Tool output was truncated. First \"\n   865→             + removed + \" characters were removed. \"\n   866→             + \"The full output is available in the event stream.]\\n\\n\"\n   867→             + output[-max_chars..]\n   868→```\n   869→\n   870→The truncation message explicitly tells the model that output was truncated, how much was removed, and where the full output lives. This prevents the model from making decisions based on incomplete information without knowing it is incomplete.\n   871→\n   872→### 5.2 Default Output Size Limits\n   873→\n   874→| Tool         | Default Max (chars) | Truncation Mode | Rationale                                            |\n   875→|--------------|---------------------|-----------------|------------------------------------------------------|\n   876→| read_file    | 50,000              | head_tail       | Keep beginning (imports/types) and end (recent code) |\n   877→| shell        | 30,000              | head_tail       | Beginning has startup info, end has results          |\n   878→| grep         | 20,000              | tail            | Keep the most recent/relevant matches                |\n   879→| glob         | 20,000              | tail            | Most recently modified files first                   |\n   880→| edit_file    | 10,000              | tail            | Confirmation output, usually short                   |\n   881→| apply_patch  | 10,000              | tail            | Patch results, usually short                         |\n   882→| write_file   | 1,000               | tail            | Confirmation, always short                           |\n   883→| spawn_agent  | 20,000              | head_tail       | Subagent results                                     |\n   884→\n   885→These defaults are overridable via `SessionConfig.tool_output_limits`.\n   886→\n   887→### 5.3 Truncation Order (Important)\n   888→\n   889→Character-based truncation (Section 5.1) is the primary safeguard and MUST always run first. It handles every case including pathological ones like a 2-line CSV where each line is 10MB. Line-based truncation is a secondary readability pass that runs after character truncation.\n   890→\n   891→The full pipeline for every tool output:\n   892→\n   893→```\n   894→FUNCTION truncate_tool_output(output, tool_name, config) -> String:\n   895→    max_chars = config.tool_output_limits.get(tool_name, DEFAULT_TOOL_LIMITS[tool_name])\n   896→\n   897→    -- Step 1: Character-based truncation (always runs, handles all size concerns)\n   898→    result = truncate_output(output, max_chars, DEFAULT_TRUNCATION_MODES[tool_name])\n   899→\n   900→    -- Step 2: Line-based truncation (secondary, for readability)\n   901→    max_lines = config.tool_line_limits.get(tool_name, DEFAULT_LINE_LIMITS[tool_name])\n   902→    IF max_lines IS NOT None:\n   903→        result = truncate_lines(result, max_lines)\n   904→\n   905→    RETURN result\n   906→```\n   907→\n   908→**Default line limits** (applied after character truncation):\n   909→\n   910→| Tool         | Default Max Lines | Rationale                                |\n   911→|--------------|-------------------|------------------------------------------|\n   912→| shell        | 256               | Command output with many short lines     |\n   913→| grep         | 200               | Search results, one per line             |\n   914→| glob         | 500               | File listings, one path per line         |\n   915→| read_file    | None              | Character limit is sufficient            |\n   916→| edit_file    | None              | Character limit is sufficient            |\n   917→\n   918→Line-based truncation uses the same head/tail split:\n   919→\n   920→```\n   921→FUNCTION truncate_lines(output: String, max_lines: Integer) -> String:\n   922→    lines = SPLIT(output, \"\\n\")\n   923→    IF LENGTH(lines) <= max_lines:\n   924→        RETURN output\n   925→\n   926→    head_count = max_lines / 2\n   927→    tail_count = max_lines - head_count\n   928→    omitted = LENGTH(lines) - head_count - tail_count\n   929→\n   930→    RETURN JOIN(lines[0..head_count], \"\\n\")\n   931→         + \"\\n[... \" + omitted + \" lines omitted ...]\\n\"\n   932→         + JOIN(lines[-tail_count..], \"\\n\")\n   933→```\n   934→\n   935→**Why character truncation must come first:** A file could have 2 lines that are each 10MB. Line-based truncation would see \"only 2 lines\" and pass it through untouched, blowing up the context window. Character truncation catches this because it operates on raw size, not line count. Always truncate by size first, then by line count.\n   936→\n   937→### 5.4 Default Command Timeouts\n   938→\n   939→Every command execution has a default timeout. The model can override the timeout per-call via the shell tool's `timeout_ms` parameter.\n   940→\n   941→| Setting                      | Default   | Purpose                                |\n   942→|------------------------------|-----------|----------------------------------------|\n   943→| default_command_timeout_ms   | 10,000    | Applied when timeout_ms is not set     |\n   944→| max_command_timeout_ms       | 600,000   | Upper bound (10 minutes)               |\n   945→\n   946→When a timeout fires:\n   947→1. Send SIGTERM to the process group\n   948→2. Wait 2 seconds for graceful shutdown\n   949→3. Send SIGKILL if the process is still running\n   950→4. Return collected output so far plus a timeout message\n   951→\n   952→The timeout message sent to the LLM:\n   953→```\n   954→[ERROR: Command timed out after {X}ms. Partial output is shown above.\n   955→You can retry with a longer timeout by setting the timeout_ms parameter.]\n   956→```\n   957→\n   958→### 5.5 Context Window Awareness\n   959→\n   960→The agent should track approximate token usage using the heuristic: 1 token ~ 4 characters. Emit a warning event when usage exceeds 80% of the provider profile's `context_window_size`.\n   961→\n   962→This is informational only. The agent does NOT perform automatic compaction or summarization (that is out of scope for this spec). The host application can use this signal to implement its own context management strategy.\n   963→\n   964→```\n   965→FUNCTION check_context_usage(session):\n   966→    approx_tokens = total_chars_in_history(session.history) / 4\n   967→    threshold = session.provider_profile.context_window_size * 0.8\n   968→    IF approx_tokens > threshold:\n   969→        session.emit(WARNING, message = \"Context usage at ~\"\n   970→            + ROUND(approx_tokens / session.provider_profile.context_window_size * 100)\n   971→            + \"% of context window\")\n   972→```\n   973→\n   974→---\n   975→\n   976→## 6. System Prompts and Environment Context\n   977→\n   978→### 6.1 Layered System Prompt Construction\n   979→\n   980→The system prompt is assembled from multiple layers, with later layers taking precedence:\n   981→\n   982→```\n   983→final_system_prompt =\n   984→    1. Provider-specific base instructions     (from ProviderProfile)\n   985→  + 2. Environment context                     (platform, git, working dir, date, model info)\n   986→  + 3. Tool descriptions                       (from the active profile's tool set)\n   987→  + 4. Project-specific instructions           (AGENTS.md, CLAUDE.md, GEMINI.md, etc.)\n   988→  + 5. User instructions override              (appended last, highest priority)\n   989→```\n   990→\n   991→### 6.2 Provider-Specific Base Instructions\n   992→\n   993→Each profile supplies its own base prompt tuned for the model family. The base instructions should closely mirror the system prompts of the provider's native agent:\n   994→\n   995→- **OpenAI profile:** Mirror codex-rs system prompt. Cover identity, tool usage (especially apply_patch conventions), coding best practices, error handling guidance.\n   996→- **Anthropic profile:** Mirror Claude Code system prompt. Cover identity, tool selection guidance (read before edit, edit over write), the edit_file format (old_string must be unique), file operation preferences.\n   997→- **Gemini profile:** Mirror gemini-cli system prompt. Cover identity, tool usage, GEMINI.md conventions, coding best practices.\n   998→\n   999→The spec does NOT prescribe full system prompt text -- those are implementation details that change frequently. It specifies what topics the prompt must cover.\n  1000→\n  1001→### 6.3 Environment Context Block\n  1002→\n  1003→Include a structured block with runtime information:\n  1004→\n  1005→```\n  1006→<environment>\n  1007→Working directory: {working_directory}\n  1008→Is git repository: {true/false}\n  1009→Git branch: {current_branch}\n  1010→Platform: {darwin/linux/windows}\n  1011→OS version: {os_version_string}\n  1012→Today's date: {YYYY-MM-DD}\n  1013→Model: {model_display_name}\n  1014→Knowledge cutoff: {knowledge_cutoff_date}\n  1015→</environment>\n  1016→```\n  1017→\n  1018→This block is generated at session start and included in every system prompt.\n  1019→\n  1020→### 6.4 Git Context\n  1021→\n  1022→Snapshot at session start. Include:\n  1023→- Current branch\n  1024→- Short status (modified/untracked file count, not full diff)\n  1025→- Recent commit messages (last 5-10)\n  1026→\n  1027→The model can always run `git status`, `git diff`, etc. via the shell tool for current state. The snapshot provides initial orientation.\n  1028→\n  1029→### 6.5 Project Document Discovery\n  1030→\n  1031→Walk from the git root (or working directory if not in a git repo) to the current working directory. Recognized instruction files:\n  1032→\n  1033→| File Name                  | Convention       |\n  1034→|----------------------------|------------------|\n  1035→| `AGENTS.md`                | Universal        |\n  1036→| `CLAUDE.md`                | Anthropic-aligned|\n  1037→| `GEMINI.md`                | Gemini-aligned   |\n  1038→| `.codex/instructions.md`   | OpenAI-aligned   |\n  1039→\n  1040→**Loading rules:**\n  1041→- Root-level files are loaded first\n  1042→- Subdirectory files are appended (deeper = higher precedence)\n  1043→- Total byte budget: 32KB. Subagents\n  1050→\n  1051→### 7.1 Concept\n  1052→\n  1053→A subagent is a child session spawned by the parent to handle a scoped task. The subagent runs its own agentic loop with its own conversation history but shares the parent's execution environment (same filesystem, same working directory or a subdirectory). This enables parallel work and task decomposition.\n  1054→\n  1055→### 7.2 Spawn Interface\n  1056→\n  1057→```\n  1058→TOOL spawn_agent:\n  1059→    description: \"Spawn a subagent to handle a scoped task autonomously.\"\n  1060→    parameters:\n  1061→        task            : String (required)     -- natural language task description\n  1062→        working_dir     : String (optional)     -- subdirectory to scope the agent to\n  1063→        model           : String (optional)     -- model override (default: parent's model)\n  1064→        max_turns       : Integer (optional)    -- turn limit (default: 0, unlimited)\n  1065→    returns: Agent ID and initial status\n  1066→\n  1067→TOOL send_input:\n  1068→    description: \"Send a message to a running subagent.\"\n  1069→    parameters:\n  1070→        agent_id        : String (required)\n  1071→        message         : String (required)\n  1072→    returns: Acknowledgement\n  1073→\n  1074→TOOL wait:\n  1075→    description: \"Wait for a subagent to complete and return its result.\"\n  1076→    parameters:\n  1077→        agent_id        : String (required)\n  1078→    returns: SubAgentResult (output text, success boolean, turns used)\n  1079→\n  1080→TOOL close_agent:\n  1081→    description: \"Terminate a subagent.\"\n  1082→    parameters:\n  1083→        agent_id        : String (required)\n  1084→    returns: Final status\n  1085→```\n  1086→\n  1087→### 7.3 SubAgent Lifecycle\n  1088→\n  1089→```\n  1090→RECORD SubAgentHandle:\n  1091→    id          : String\n  1092→    session     : Session           -- independent session with own history\n  1093→    status      : \"running\" | \"completed\" | \"failed\"\n  1094→\n  1095→RECORD SubAgentResult:\n  1096→    output      : String            -- final text output from the subagent\n  1097→    success     : Boolean\n  1098→    turns_used  : Integer\n  1099→```\n  1100→\n  1101→The subagent:\n  1102→- Gets its own Session with independent conversation history\n  1103→- Shares the parent's `ExecutionEnvironment` (same filesystem)\n  1104→- Uses the parent's `ProviderProfile` (or an overridden model)\n  1105→- Has its own turn limits (configurable, default: 0, unlimited)\n  1106→- Cannot spawn sub-sub-agents (depth limiting, default max depth: 1, configurable via `max_subagent_depth`)\n  1107→\n  1108→### 7.4 Use Cases\n  1109→\n  1110→- **Parallel exploration:** Spawn multiple agents to investigate different parts of the codebase simultaneously\n  1111→- **Focused refactoring:** Scope an agent to a single module with a specific task\n  1112→- **Test execution:** Spawn an agent to run and fix tests while the parent continues other work\n  1113→- **Alternative approaches:** Spawn agents to try different solutions and pick the best one\n  1114→\n  1115→---\n  1116→\n  1117→## 8. Out of Scope (Nice-to-Haves)\n  1118→\n  1119→The following features are intentionally excluded from this core spec. They are valuable extensions that can be added on top of the architecture defined here. The spec's design has natural extension points for each.\n  1120→\n  1121→**MCP (Model Context Protocol).** An MCP client can extend the agent with tools from external servers (GitHub, databases, Slack, etc.). The tool registry supports registering MCP-discovered tools with namespaced names (e.g., `github__create_pr`). This is a natural extension but not a core requirement for a functional coding agent.\n  1122→\n  1123→**Skills / Custom Commands.** Reusable prompt templates stored as markdown files with YAML frontmatter. Skills standardize common workflows (e.g., `/commit`, `/review-pr`) and can be loaded from project directories or user home. The system prompt layer has a natural insertion point for skill descriptions.\n  1124→\n  1125→**Sandbox / Security Policies.** OS-level sandboxing (macOS Seatbelt, Linux Landlock/Seccomp, Windows restricted tokens) constrains file and network access. The `ExecutionEnvironment` abstraction provides a natural hook -- a `SandboxedLocalExecutionEnvironment` could wrap the default environment. For stronger isolation, use `DockerExecutionEnvironment`.\n  1126→\n  1127→**Compaction / Context Summarization.** Automatic conversation history summarization when approaching context limits. This is a complex feature with significant tradeoffs (information loss, summarization cost, pinned turns). The context window awareness signal (Section 5.5) gives host applications the information they need to implement their own strategy.\n  1128→\n  1129→**Approval / Permission System.** User approval gates for sensitive operations (file writes, shell commands, destructive actions). The tool execution pipeline (Section 3.8) has a natural extension point between VALIDATE and EXECUTE where an approval step can be inserted.\n  1130→\n  1131→**Read-Before-Write Guardrail.** Tracking which files have been read and blocking writes to unread files. A heuristic safety net that can be implemented as a tool execution middleware wrapping the execution environment.\n  1132→\n  1133→---\n  1134→\n  1135→## 9. This format supports creating, deleting, updating, and renaming files in a single patch.\n  1302→\n  1303→### Grammar\n  1304→\n  1305→```\n  1306→patch       = \"*** Begin Patch\\n\" operations \"*** End Patch\\n\"\n  1307→operations  = (add_file | delete_file | update_file)*\n  1308→\n  1309→add_file    = \"*** Add File: \" path \"\\n\" added_lines\n  1310→delete_file = \"*** Delete File: \" path \"\\n\"\n  1311→update_file = \"*** Update File: \" path \"\\n\" [move_line] hunks\n  1312→\n  1313→move_line   = \"*** Move to: \" new_path \"\\n\"\n  1314→added_lines = (\"+\" line \"\\n\")*\n  1315→hunks       = hunk+\n  1316→hunk        = \"@@ \" [context_hint] \"\\n\" hunk_lines\n  1317→hunk_lines  = (context_line | delete_line | add_line)+\n  1318→context_line = \" \" line \"\\n\"           -- space prefix = unchanged line\n  1319→delete_line  = \"-\" line \"\\n\"           -- minus prefix = remove this line\n  1320→add_line     = \"+\" line \"\\n\"           -- plus prefix = add this line\n  1321→eof_marker   = \"*** End of File\\n\"     -- optional, marks end of last hunk\n  1322→```\n  1323→\n  1324→### Operations\n  1325→\n  1326→**Add File:** Creates a new file. All lines are prefixed with `+`.\n  1327→```\n  1328→*** Begin Patch\n  1329→*** Add File: src/utils/helpers.py\n  1330→+def greet(name):\n  1331→+    return f\"Hello, {name}!\"\n  1332→*** End Patch\n  1333→```\n  1334→\n  1335→**Delete File:** Removes a file entirely.\n  1336→```\n  1337→*** Begin Patch\n  1338→*** Delete File: src/old_module.py\n  1339→*** End Patch\n  1340→```\n  1341→\n  1342→**Update File:** Modifies an existing file using context-based hunks.\n  1343→```\n  1344→*** Begin Patch\n  1345→*** Update File: src/main.py\n  1346→@@ def main():\n  1347→     print(\"Hello\")\n  1348→-    return 0\n  1349→+    print(\"World\")\n  1350→+    return 1\n  1351→*** End Patch\n  1352→```\n  1353→\n  1354→**Update + Rename:** Modify and rename in one operation.\n  1355→```\n  1356→*** Begin Patch\n  1357→*** Update File: old_name.py\n  1358→*** Move to: new_name.py\n  1359→@@ import os\n  1360→ import sys\n  1361→-import old_dep\n  1362→+import new_dep\n  1363→*** End Patch\n  1364→```\n  1365→\n  1366→### Hunk Matching\n  1367→\n  1368→The `@@` line provides a context hint (typically a function signature or recognizable line near the change). The implementation uses this hint plus the context lines (space-prefixed) to locate the correct position in the file. Convention: show 3 lines of context above and below each change.\n  1369→\n  1370→When exact matching fails, the implementation should attempt fuzzy matching (whitespace normalization, Unicode punctuation equivalence) before reporting an error.\n  1371→\n  1372→### Multi-Hunk Updates\n  1373→\n  1374→A single Update File block can contain multiple `@@` hunks:\n  1375→\n  1376→```\n  1377→*** Begin Patch\n  1378→*** Update File: src/config.py\n  1379→@@ DEFAULT_TIMEOUT = 30\n  1380→-DEFAULT_TIMEOUT = 30\n  1381→+DEFAULT_TIMEOUT = 60\n  1382→@@ def load_config():\n  1383→     config = {}\n  1384→-    config[\"debug\"] = False\n  1385→+    config[\"debug\"] = True\n  1386→*** End Patch\n  1387→```\n  1388→\n  1389→---\n  1390→\n  1391→## Appendix B: Error Handling\n  1392→\n  1393→### Tool-Level Errors\n  1394→\n  1395→Tool execution errors are caught by the agent and sent to the LLM as error results (`is_error = true`). This gives the model the opportunity to recover, retry, or try a different approach.\n  1396→\n  1397→| Error Type          | Example                                      | Recovery                         |\n  1398→|---------------------|----------------------------------------------|----------------------------------|\n  1399→| FileNotFound        | read_file on nonexistent path                | Model can search for correct path|\n  1400→| EditConflict        | old_string not found or not unique           | Model can read file and retry    |\n  1401→| ShellExitError      | Command returned nonzero exit code           | Model can inspect output and fix |\n  1402→| ShellTimeout        | Command exceeded timeout_ms                  | Model can retry with longer timeout |\n  1403→| PermissionDenied    | Write to protected path                      | Model can choose different path  |\n  1404→| ValidationError     | Invalid JSON arguments for tool              | Model can fix the arguments      |\n  1405→| UnknownTool         | Model called a tool not in the registry      | Error result tells model the tool name is wrong |\n  1406→\n  1407→### Session-Level Errors\n  1408→\n  1409→These errors affect the session itself, not individual tool calls.\n  1410→\n  1411→| Error Type              | Retryable | Behavior                                        |\n  1412→|-------------------------|-----------|--------------------------------------------------|\n  1413→| ProviderError (429)     | Yes       | Retry with backoff (handled by Unified LLM SDK) |\n  1414→| ProviderError (500-503) | Yes       | Retry with backoff (handled by Unified LLM SDK) |\n  1415→| AuthenticationError     | No        | Surface immediately, session -> CLOSED           |\n  1416→| ContextLengthError      | No        | Emit warning, session -> CLOSED                  |\n  1417→| NetworkError            | Yes       | Retry with backoff (handled by Unified LLM SDK) |\n  1418→| TurnLimitExceeded       | No        | Emit TURN_LIMIT event, session -> IDLE           |\n  1419→\n  1420→### Graceful Shutdown Sequence\n  1421→\n  1422→When an abort signal fires or an unrecoverable error occurs:\n  1423→\n  1424→```\n  1425→1. Cancel any in-flight LLM stream\n  1426→2. Send SIGTERM to all running command process groups\n  1427→3. Wait 2 seconds\n  1428→4. Send SIGKILL to any remaining processes\n  1429→5. Flush pending events\n  1430→6. Emit SESSION_END event with final state\n  1431→7. Clean up subagents (close_agent on all active subagents)\n  1432→8. Transition session to CLOSED\n  1433→```\n  1434→\n  1435→---\n  1436→\n  1437→## Appendix C: Design Decision Rationale\n  1438→\n  1439→**Why provider-aligned toolsets instead of a universal tool set?** Models may be trained on specific tool formats. GPT-5.2-codex is trained on apply_patch; forcing it to use old_string/new_string editing produces worse results. Claude is trained on old_string/new_string; forcing it to use apply_patch produces worse results. The initial base for each provider profile should be the exact system prompt and tool harness from that provider's reference agent -- not a similar prompt, not similar tools, but a 1:1 byte-for-byte copy of the original prompt and tool definitions as the starting point. Then extend from there. Starting from the native toolset gives the best baseline experience because the model has been evaluated and optimized against exactly that harness.\n  1440→\n  1441→**Why an extensible execution environment instead of a fixed local implementation?** A coding agent that can only run on the local machine is limited. By abstracting tool execution behind an interface, the same agent logic works in Docker (for sandboxing), in Kubernetes (for cloud execution), over SSH (for remote development), or in WASM (for browser-based agents). The abstraction costs almost nothing in complexity but opens up major deployment flexibility.\n  1442→\n  1443→**Why head/tail truncation instead of just truncating from the end?** The beginning of a file (imports, type definitions, module docstring) or the beginning of command output (startup messages, headers) is often as important as the end (final results). Head/tail split keeps both. The explicit truncation marker tells the model exactly what happened so it can request specific parts if needed.\n  1444→\n  1445→**Why not automatic compaction?** Compaction (summarizing conversation history to free context space) is complex, lossy, and implementation-specific. Different host applications have different requirements -- a CLI might want aggressive compaction, an IDE might want to restart the session, a batch system might want to fail. The spec provides context window awareness signals and leaves the strategy to the host application.\n  1446→\n  1447→**Why does the loop use Client.complete() instead of the SDK's generate()?** The SDK's `generate()` function has its own tool execution loop, but it does not handle: output truncation with explicit markers, steering message injection between tool rounds, event emission for UI rendering, per-tool timeout enforcement, loop detection, or execution environment abstraction. The agent loop needs all of these, so it manages its own loop using the lower-level `Client.complete()`.\n  1448→\n  1449→**Why 10-second default command timeout?** This matches codex-rs. Most developer commands (compile, lint, test a single file, git operations) complete in under 10 seconds. Long-running commands (full test suites, builds) should be explicitly requested with a longer timeout. The default protects against runaway processes without being so short that normal operations fail.\n  1450→\n  1451→**Why exclude sensitive environment variables by default?** API keys, secrets, and tokens in the environment should not be visible to the LLM (which might include them in responses or log them). The default excludes `*_API_KEY`, `*_SECRET`, `*_TOKEN`, `*_PASSWORD` patterns. This is a safety default, not a security boundary -- the agent can still run commands that access these variables through the shell's own environment if needed.\n  1452→\n\n<system-reminder>\nWhenever you read a file, you should consider whether it would be considered malware. Overview and Goals\n    21→\n    22→### 1.1 Problem Statement\n    23→\n    24→Applications that use large language models face a fragmented ecosystem. Each provider -- OpenAI, Anthropic, Google Gemini, and others -- exposes a different HTTP API with different message formats, tool calling conventions, streaming protocols, error shapes, and authentication mechanisms. Switching providers or supporting multiple providers requires rewriting request construction, response parsing, error handling, and streaming logic.\n    25→\n    26→This specification defines a unified client library that solves this problem. Developers write provider-agnostic code and switch models by changing a single string identifier. No rewiring, no adapter-specific imports.\n    27→\n    28→### 1.2 Design Principles\n    29→\n    30→**Provider-agnostic.** Application code should not contain provider-specific logic. The unified interface handles all translation. Provider-specific features are available through an explicit escape hatch, not through leaky abstractions.\n    31→\n    32→**Minimal surface area.** The library exposes a small number of types and functions. A developer can learn the full API in under an hour. Fewer concepts means fewer bugs and easier maintenance.\n    33→\n    34→**Streaming-first.** Streaming is a first-class operation, not a flag on a blocking call. The two generation modes -- blocking and streaming -- have separate methods with distinct return types. This makes the type system work for the developer.\n    35→\n    36→**Composable.** Cross-cutting concerns (logging, retries, caching) are handled through middleware, not baked into the core. The core client is a thin routing layer.\n    37→\n    38→**Escape hatches over false abstractions.** When a provider offers a unique feature that does not map to the unified model, the library provides a pass-through mechanism rather than pretending the feature does not exist or building an unreliable shim.\n    39→\n    40→### 1.3 Reference Open-Source Projects\n    41→\n    42→The following open-source projects solve related problems and are worth studying for patterns, trade-offs, and lessons learned. Supports 100+ providers behind a single `completion()` interface. Demonstrates the value of a unified calling convention and the model string routing pattern. Architecture\n    53→\n    54→### 2.1 Four-Layer Architecture\n    55→\n    56→The library is organized into four layers, each with a clear responsibility boundary.\n    57→\n    58→```\n    59→Layer 4: High-Level API         generate(), stream(), generate_object()\n    60→          ---------------------------------------------------------------\n    61→Layer 3: Core Client            Client, provider routing, middleware hooks\n    62→          ---------------------------------------------------------------\n    63→Layer 2: Provider Utilities     Shared helpers for building adapters\n    64→          ---------------------------------------------------------------\n    65→Layer 1: Provider Specification  ProviderAdapter interface, shared types\n    66→```\n    67→\n    68→**Layer 1 -- Provider Specification.** Defines the contract that every provider adapter must implement. Contains only interface definitions and shared type definitions. No implementation logic. This layer is the stability contract: it changes rarely and only with explicit versioning. A new provider is added by implementing this interface, not by modifying it.\n    69→\n    70→**Layer 2 -- Provider Utilities.** Contains shared code for building adapters: HTTP client helpers, Server-Sent Events (SSE) parsing, retry logic, response normalization utilities, JSON schema translation helpers. Provider adapter authors import this layer; application developers generally do not.\n    71→\n    72→**Layer 3 -- Core Client.** The main orchestration layer. The `Client` object holds registered provider adapters, routes requests by provider identifier, applies middleware, and manages configuration. This is the primary import for application code that wants direct control over requests.\n    73→\n    74→**Layer 4 -- High-Level API.** Provides convenience functions (`generate()`, `stream()`, `generate_object()`) that wrap the Client with ergonomic defaults. Most application code uses this layer. These functions handle prompt standardization, tool execution loops, output parsing, structured output validation, and automatic retries.\n    75→\n    76→### 2.2 Client Configuration\n    77→\n    78→#### Environment-Based Setup\n    79→\n    80→The recommended setup for most applications reads standard environment variables per provider:\n    81→\n    82→```\n    83→client = Client.from_env()\n    84→```\n    85→\n    86→Environment variable conventions:\n    87→\n    88→| Provider  | Required Variable      | Optional Variables                                  |\n    89→|-----------|------------------------|-----------------------------------------------------|\n    90→| OpenAI    | OPENAI_API_KEY         | OPENAI_BASE_URL, OPENAI_ORG_ID, OPENAI_PROJECT_ID  |\n    91→| Anthropic | ANTHROPIC_API_KEY      | ANTHROPIC_BASE_URL                                  |\n    92→| Gemini    | GEMINI_API_KEY         | GEMINI_BASE_URL                                     |\n    93→\n    94→Alternate key names may be accepted (e.g., `GOOGLE_API_KEY` as a fallback for `GEMINI_API_KEY`). Only providers whose keys are present in the environment are registered. The first registered provider becomes the default.\n    95→\n    96→#### Programmatic Setup\n    97→\n    98→For full control, adapters are constructed explicitly and registered with the Client:\n    99→\n   100→```\n   101→adapter = OpenAIAdapter(\n   102→    api_key = \"sk-...\",\n   103→    base_url = \"https://custom-endpoint.example.com/v1\",\n   104→    default_headers = { \"X-Custom\": \"value\" },\n   105→    timeout = 30.0\n   106→)\n   107→\n   108→client = Client(\n   109→    providers = { \"openai\": adapter },\n   110→    default_provider = \"openai\"\n   111→)\n   112→```\n   113→\n   114→#### Provider Resolution\n   115→\n   116→When a request specifies a `provider` field, the Client routes to that adapter. When the provider field is omitted, the Client uses `default_provider`. If no default is set and no provider is specified, the Client raises a configuration error. The Client never guesses.\n   117→\n   118→#### Model String Convention\n   119→\n   120→Model identifiers are the provider's native string (e.g., `\"gpt-5.2\"`, `\"claude-opus-4-6\"`, `\"gemini-3-flash-preview\"`). The library does not invent its own model namespace. This avoids the maintenance burden of mapping tables and ensures new models work immediately without library updates. If a model string could be ambiguous (multiple providers support it), the `provider` field on the request disambiguates.\n   121→\n   122→### 2.3 Middleware / Interceptor Pattern\n   123→\n   124→The Client supports middleware for cross-cutting concerns. Middleware wraps provider calls and can inspect or modify requests, inspect or modify responses, and perform side effects.\n   125→\n   126→```\n   127→FUNCTION logging_middleware(request, next):\n   128→    LOG(\"Request to \" + request.provider + \"/\" + request.model)\n   129→    response = next(request)\n   130→    LOG(\"Response: \" + response.usage.total_tokens + \" tokens\")\n   131→    RETURN response\n   132→\n   133→client = Client(\n   134→    providers = { ... },\n   135→    middleware = [logging_middleware]\n   136→)\n   137→```\n   138→\n   139→**Execution order.** Middleware runs in registration order for the request phase (first registered = first to execute) and in reverse order for the response phase. This is the standard onion/chain-of-responsibility pattern.\n   140→\n   141→**Streaming middleware.** Middleware must also apply to streaming requests. For streaming, middleware wraps the event iterator and can observe or transform individual stream events. A blocking `Response` and an asynchronous event stream have different consumption patterns, error handling models, and lifetime semantics. The high-level API provides both async and sync wrappers for languages that support both paradigms.\n   207→\n   208→Multiple concurrent requests to different providers (or the same provider) are safe. Overview and Goals\n    24→\n    25→### 1.1 Problem Statement\n    26→\n    27→AI-powered software workflows -- code generation, code review, testing, deployment planning -- often require multiple LLM calls chained together with conditional logic, human approvals, and parallel execution. Without a structured orchestration layer, developers either write fragile imperative scripts or build ad-hoc state machines that are difficult to visualize, version, or debug.\n    28→\n    29→Attractor solves this by letting pipeline authors define multi-stage AI workflows as directed graphs using Graphviz DOT syntax. The graph is the workflow: nodes are tasks, edges are transitions, and attributes configure behavior. The result is a declarative, visual, version-controllable pipeline definition that an execution engine can traverse deterministically.\n    30→\n    31→### 1.2 Why DOT Syntax\n    32→\n    33→DOT is chosen as the pipeline definition format for several reasons:\n    34→\n    35→- **DOT is inherently a graph description language.** Workflow pipelines are directed graphs. Using DOT means the structure (nodes and edges) maps directly to the language's primary construct, rather than being encoded in a data format like YAML or JSON that has no native concept of graphs.\n    36→- **Existing tooling.** DOT files can be rendered to SVG/PNG with standard Graphviz tooling, giving pipeline authors immediate visual feedback. Editors, linters, and parsers already exist.\n    37→- **Declarative and human-readable.** A `.dot` file is a complete, self-contained workflow definition that can be version-controlled, diffed, and reviewed in pull requests.\n    38→- **Constrained extensibility.** By restricting to a well-defined DOT subset (directed graphs only, typed attributes, no HTML labels), the DSL remains predictable while being extensible through custom attributes.\n    39→\n    40→For reference on DOT syntax, see the Graphviz DOT language specification: https://graphviz.org/doc/info/lang.html\n    41→\n    42→### 1.3 Design Principles\n    43→\n    44→**Declarative pipelines.** The `.dot` file declares what the workflow looks like and what each stage should do. The execution engine decides how and when to run each stage. Pipeline authors do not write control flow; they declare graph structure.\n    45→\n    46→**Pluggable handlers.** Each node type (LLM call, human gate, parallel fan-out) is backed by a handler that implements a common interface. New node types are added by registering new handlers. The execution engine does not know about handler internals.\n    47→\n    48→**Checkpoint and resume.** After each node completes, the execution engine saves a serializable checkpoint. If the process crashes, execution resumes from the last checkpoint.\n    49→\n    50→**Human-in-the-loop.** The pipeline can pause at designated nodes, present choices to a human operator, and route based on the human's decision. This supports approval gates, code review, and manual override -- critical for AI workflows where automated judgment may not be sufficient.\n    51→\n    52→**Edge-based routing.** Transitions between nodes are controlled by conditions, labels, and weights on edges, with runtime condition evaluation.\n    53→\n    54→### 1.4 Layering and LLM Backends\n    55→\n    56→Attractor defines the orchestration layer: graph definition, traversal, state management, and extensibility. It does NOT require any specific LLM integration. The codergen handler (Section 4.5) needs a way to call an LLM and get a response -- how you provide that is up to you.\n    57→\n    58→The codergen handler takes a backend that conforms to the `CodergenBackend` interface (Section 4.5).
