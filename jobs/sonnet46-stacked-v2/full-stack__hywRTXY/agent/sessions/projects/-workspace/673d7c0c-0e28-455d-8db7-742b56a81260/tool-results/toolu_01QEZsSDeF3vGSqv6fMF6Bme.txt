     1→# Unified LLM Client Specification
     2→
     3→This document is a consolidated, language-agnostic specification for building a unified client library that provides a single interface across multiple LLM providers (OpenAI, Anthropic, Google Gemini, and others). It is designed to be implementable from scratch by any developer or coding agent in any programming language.

    20→## 1. Overview and Goals
    21→
    22→### 1.1 Problem Statement
    23→
    24→Applications that use large language models face a fragmented ecosystem. Each provider -- OpenAI, Anthropic, Google Gemini, and others -- exposes a different HTTP API with different message formats, tool calling conventions, streaming protocols, error shapes, and authentication mechanisms. Switching providers or supporting multiple providers requires rewriting request construction, response parsing, error handling, and streaming logic.
    25→
    26→This specification defines a unified client library that solves this problem. Developers write provider-agnostic code and switch models by changing a single string identifier. No rewiring, no adapter-specific imports.
    27→
    28→### 1.2 Design Principles
    29→
    30→**Provider-agnostic.** Application code should not contain provider-specific logic. The unified interface handles all translation. Provider-specific features are available through an explicit escape hatch, not through leaky abstractions.
    31→
    32→**Minimal surface area.** The library exposes a small number of types and functions. A developer can learn the full API in under an hour. Fewer concepts means fewer bugs and easier maintenance.
    33→
    34→**Streaming-first.** Streaming is a first-class operation, not a flag on a blocking call. The two generation modes -- blocking and streaming -- have separate methods with distinct return types. This makes the type system work for the developer.
    35→
    36→**Composable.** Cross-cutting concerns (logging, retries, caching) are handled through middleware, not baked into the core. The core client is a thin routing layer.
    37→
    38→**Escape hatches over false abstractions.** When a provider offers a unique feature that does not map to the unified model, the library provides a pass-through mechanism rather than pretending the feature does not exist or building an unreliable shim.
    39→
    40→### 1.3 Reference Open-Source Projects
    41→
    42→The following open-source projects solve related problems and are worth studying for patterns, trade-offs, and lessons learned. They are not dependencies; implementors may take inspiration from any combination of them.
    43→
    44→- **Vercel AI SDK** (https://github.com/vercel/ai) -- TypeScript. Multi-provider architecture with a versioned provider specification. Clean separation between provider interfaces and high-level convenience API (`generateText`/`streamText`/`generateObject`). Demonstrates the start/delta/end streaming event pattern and a composable middleware system.
    45→
    46→- **LiteLLM** (https://github.com/BerriAI/litellm) -- Python. Supports 100+ providers behind a single `completion()` interface. Demonstrates the value of a unified calling convention and the model string routing pattern. Shows how to handle the long tail of provider-specific quirks at scale.
    47→
    48→- **pi-ai** (https://github.com/badlogic/pi-mono/tree/main/packages/ai) -- TypeScript. A multi-provider AI client from @mariozechner's pi-mono project. Demonstrates cost tracking, usage aggregation, and a clean provider adapter pattern with explicit reasoning token support.

    52→## 2. Architecture
    53→
    54→### 2.1 Four-Layer Architecture
    55→
    56→The library is organized into four layers, each with a clear responsibility boundary.
    57→
    58→```
    59→Layer 4: High-Level API         generate(), stream(), generate_object()
    60→          ---------------------------------------------------------------
    61→Layer 3: Core Client            Client, provider routing, middleware hooks
    62→          ---------------------------------------------------------------
    63→Layer 2: Provider Utilities     Shared helpers for building adapters
    64→          ---------------------------------------------------------------
    65→Layer 1: Provider Specification  ProviderAdapter interface, shared types
    66→```
    67→
    68→**Layer 1 -- Provider Specification.** Defines the contract that every provider adapter must implement. Contains only interface definitions and shared type definitions. No implementation logic. This layer is the stability contract: it changes rarely and only with explicit versioning. A new provider is added by implementing this interface, not by modifying it.
    69→
    70→**Layer 2 -- Provider Utilities.** Contains shared code for building adapters: HTTP client helpers, Server-Sent Events (SSE) parsing, retry logic, response normalization utilities, JSON schema translation helpers. Provider adapter authors import this layer; application developers generally do not.
    71→
    72→**Layer 3 -- Core Client.** The main orchestration layer. The `Client` object holds registered provider adapters, routes requests by provider identifier, applies middleware, and manages configuration. This is the primary import for application code that wants direct control over requests.
    73→
    74→**Layer 4 -- High-Level API.** Provides convenience functions (`generate()`, `stream()`, `generate_object()`) that wrap the Client with ergonomic defaults. Most application code uses this layer. These functions handle prompt standardization, tool execution loops, output parsing, structured output validation, and automatic retries.
    75→
    76→### 2.2 Client Configuration
    77→
    78→#### Environment-Based Setup
    79→
    80→The recommended setup for most applications reads standard environment variables per provider:
    81→
    82→```
    83→client = Client.from_env()
    84→```
    85→
    86→Environment variable conventions:
    87→
    88→| Provider  | Required Variable      | Optional Variables                                  |
    89→|-----------|------------------------|-----------------------------------------------------|
    90→| OpenAI    | OPENAI_API_KEY         | OPENAI_BASE_URL, OPENAI_ORG_ID, OPENAI_PROJECT_ID  |
    91→| Anthropic | ANTHROPIC_API_KEY      | ANTHROPIC_BASE_URL                                  |
    92→| Gemini    | GEMINI_API_KEY         | GEMINI_BASE_URL                                     |
    93→
    94→Alternate key names may be accepted (e.g., `GOOGLE_API_KEY` as a fallback for `GEMINI_API_KEY`). Only providers whose keys are present in the environment are registered. The first registered provider becomes the default.
    95→
    96→#### Programmatic Setup
    97→
    98→For full control, adapters are constructed explicitly and registered with the Client:
    99→
   100→```
   101→adapter = OpenAIAdapter(
   102→    api_key = "sk-...",
   103→    base_url = "https://custom-endpoint.example.com/v1",
   104→    default_headers = { "X-Custom": "value" },
   105→    timeout = 30.0
   106→)
   107→
   108→client = Client(
   109→    providers = { "openai": adapter },
   110→    default_provider = "openai"
   111→)
   112→```
   113→
   114→#### Provider Resolution
   115→
   116→When a request specifies a `provider` field, the Client routes to that adapter. When the provider field is omitted, the Client uses `default_provider`. If no default is set and no provider is specified, the Client raises a configuration error. The Client never guesses.
   117→
   118→#### Model String Convention
   119→
   120→Model identifiers are the provider's native string (e.g., `"gpt-5.2"`, `"claude-opus-4-6"`, `"gemini-3-flash-preview"`). The library does not invent its own model namespace. This avoids the maintenance burden of mapping tables and ensures new models work immediately without library updates. If a model string could be ambiguous (multiple providers support it), the `provider` field on the request disambiguates.
   121→
   122→### 2.3 Middleware / Interceptor Pattern
   123→
   124→The Client supports middleware for cross-cutting concerns. Middleware wraps provider calls and can inspect or modify requests, inspect or modify responses, and perform side effects.
   125→
   126→```
   127→FUNCTION logging_middleware(request, next):
   128→    LOG("Request to " + request.provider + "/" + request.model)
   129→    response = next(request)
   130→    LOG("Response: " + response.usage.total_tokens + " tokens")
   131→    RETURN response
   132→
   133→client = Client(
   134→    providers = { ... },
   135→    middleware = [logging_middleware]
   136→)
   137→```
   138→
   139→**Execution order.** Middleware runs in registration order for the request phase (first registered = first to execute) and in reverse order for the response phase. This is the standard onion/chain-of-responsibility pattern.
   140→
   141→**Streaming middleware.** Middleware must also apply to streaming requests. For streaming, middleware wraps the event iterator and can observe or transform individual stream events. The middleware interface should support both modes:
   142→
   143→```
   144→FUNCTION streaming_middleware(request, next):
   145→    event_iterator = next(request)
   146→    FOR EACH event IN event_iterator:
   147→        log_event(event)
   148→        YIELD event
   149→```
   150→
   151→**Common middleware use cases:**
   152→- Logging
   153→- Request/response caching
   154→- Cost tracking and budgets
   155→- Client-side rate limiting
   156→- Prompt injection detection
   157→- Circuit breaker pattern
   158→
   159→### 2.4 Provider Adapter Interface
   160→
   161→Every provider must implement this interface:
   162→
   163→```
   164→INTERFACE ProviderAdapter:
   165→    PROPERTY name : String             -- e.g., "openai", "anthropic", "gemini"
   166→
   167→    FUNCTION complete(request: Request) -> Response
   168→        -- Send a request, block until the model finishes, return the full response.
   169→
   170→    FUNCTION stream(request: Request) -> AsyncIterator<StreamEvent>
   171→        -- Send a request, return an asynchronous iterator of stream events.
   172→```
   173→
   174→**Why two methods, not one.** A single method with a `stream: boolean` flag was rejected because the return types are fundamentally different. A blocking `Response` and an asynchronous event stream have different consumption patterns, error handling models, and lifetime semantics. Separate methods make the type system work for the developer.
   175→
   176→**No separate `send_tool_outputs` method.** Tool results are sent by including them in the message history of a new `complete()` or `stream()` call. This matches how Anthropic and Gemini work natively. The OpenAI adapter handles any translation internally.
   177→
   178→#### Optional Adapter Methods
   179→
   180→These methods are recommended but not required:
   181→
   182→```
   183→FUNCTION close() -> Void
   184→    -- Release resources (HTTP connections, etc.). Called by Client.close().
   185→
   186→FUNCTION initialize() -> Void
   187→    -- Validate configuration on startup. Called by Client on registration.
   188→
   189→FUNCTION supports_tool_choice(mode: String) -> Boolean
   190→    -- Query whether a particular tool choice mode is supported.
   191→```
   192→
   193→### 2.5 Module-Level Default Client
   194→
   195→High-level functions (`generate()`, `stream()`, etc.) use a module-level default client. This client is lazily initialized from environment variables on first use. Applications can override it:
   196→
   197→```
   198→set_default_client(my_client)
   199→
   200→-- Or pass explicitly per call:
   201→result = generate(model = "...", prompt = "...", client = my_client)
   202→```
   203→
   204→### 2.6 Concurrency Model
   205→
   206→The library is async-first. All provider calls are non-blocking. The `complete()` and `stream()` methods are asynchronous. The high-level API provides both async and sync wrappers for languages that support both paradigms.
   207→
   208→Multiple concurrent requests to different providers (or the same provider) are safe. The Client holds no mutable state between requests. Provider adapters manage their own connection pools and must be safe for concurrent use.
   209→
   210→### 2.7 Native API Usage (Critical)
   211→
   212→Each provider adapter MUST use the provider's native, preferred API -- not a compatibility layer. This is a fundamental design requirement. Using a lowest-common-denominator compatibility layer (such as only targeting the OpenAI Chat Completions API shape) loses access to provider-specific capabilities like reasoning tokens, extended thinking, prompt caching, and advanced tool features.
   213→
   214→| Provider  | Required API                    | Why Not Compatibility Layer                                                |
   215→|-----------|---------------------------------|---------------------------------------------------------------------------|
   216→| OpenAI    | **Responses API** (`/v1/responses`) | The Responses API properly surfaces reasoning tokens, supports built-in tools (web search, file search, code interpreter), and is OpenAI's forward-looking API. The Chat Completions API does not return reasoning tokens for reasoning models (GPT-5.2 series, etc.) and lacks server-side conversation state. |
   217→| Anthropic | **Messages API** (`/v1/messages`)   | The Messages API supports extended thinking with thinking blocks and signatures, prompt caching with `cache_control`, beta feature headers, and the strict user/assistant alternation model. There is no alternative. |
   218→| Gemini    | **Gemini API** (`/v1beta/models/*/generateContent`) | The native Gemini API supports grounding with Google Search, code execution, system instructions, and cached content. OpenAI-compatible endpoints for Gemini are limited shims. |
   219→
   220→The unified SDK abstracts over these different APIs so that callers write provider-agnostic code, but internally each adapter speaks the provider's native protocol. This is the entire value proposition: the complexity of three different APIs is handled once in the adapters so that downstream consumers (like a coding agent) never have to think about it.
   221→
   222→### 2.8 Provider Beta Headers and Feature Flags
   223→
   224→Providers frequently gate new features behind beta headers or feature flags. The unified SDK must support passing these through cleanly.
   225→
   226→**Anthropic beta headers.** Anthropic uses the `anthropic-beta` header to enable features like:
   227→- `max-tokens-3-5-sonnet-2025-04-14` -- enables 1M token context for certain models
   228→- `interleaved-thinking-2025-05-14` -- enables interleaved thinking blocks
   229→- `token-efficient-tools-2025-02-19` -- more efficient tool token usage
   230→- `prompt-caching-2024-07-31` -- enables prompt caching
   231→
   232→These must be passed as HTTP headers on the request. The adapter should accept them via `provider_options`:
   233→
   234→```
   235→request = Request(
   236→    model = "claude-opus-4-6",
   237→    messages = [ ... ],
   238→    provider_options = {
   239→        "anthropic": {
   240→            "beta_headers": ["interleaved-thinking-2025-05-14"]
   241→        }
   242→    }
   243→)
   244→```
   245→
   246→The Anthropic adapter joins these into a comma-separated `anthropic-beta` header value.
   247→
   248→**OpenAI feature flags.** The Responses API supports enabling built-in tools and features via the request body (e.g., `tools: [{"type": "web_search_preview"}]`). These should be supported through `provider_options` or by extending the tool definitions.
   249→
   250→**Gemini configuration.** Gemini supports safety settings, grounding configuration, and cached content references as part of the request body. These should be passable through `provider_options`.
   251→
   252→The key principle: the unified interface handles the common 90% of cases. The `provider_options` escape hatch handles the remaining 10% without requiring library changes for every new provider feature.
   253→
   254→### 2.9 Model Catalog
   255→
   256→The SDK should ship with a catalog of known models to help consumers (especially AI coding agents) select valid model identifiers without guessing or hallucinating model names. The catalog is advisory, not restrictive -- unknown model strings are still passed through to the provider.
   257→
   258→```
   259→RECORD ModelInfo:
   260→    id              : String            -- the model's API identifier (e.g., "claude-opus-4-6")
   261→    provider        : String            -- which provider serves this model
   262→    display_name    : String            -- human-readable name (e.g., "Claude Opus 4.6")
   263→    context_window  : Integer           -- maximum total tokens (input + output)
   264→    max_output      : Integer | None    -- maximum output tokens
   265→    supports_tools  : Boolean           -- whether the model supports tool calling
   266→    supports_vision : Boolean           -- whether the model accepts image inputs
   267→    supports_reasoning : Boolean        -- whether the model produces reasoning tokens
   268→    input_cost_per_million  : Float | None  -- cost per 1M input tokens (USD)
   269→    output_cost_per_million : Float | None  -- cost per 1M output tokens (USD)
   270→    aliases         : List<String>      -- shorthand names (e.g., ["sonnet", "claude-sonnet"])
   271→```
   272→
   273→**At the time of writing (February 2026),** the top models available through each provider's API are:
   274→
   275→| Provider  | Top Model(s)                                        |
   276→|-----------|-----------------------------------------------------|
   277→| Anthropic | **Claude Opus 4.6**, Claude Sonnet 4.5               |
   278→| OpenAI    | **GPT-5.2 series** (GPT-5.2, GPT-5.2-codex)        |
   279→| Gemini    | **Gemini 3 Pro (Preview)**, Gemini 3 Flash (Preview) |
   280→
   281→Implementations should default to the latest available models when no model is specified by the caller, and should prefer newer models in any model selection logic. However, the catalog must also include older models that are still served by the APIs, as callers may need them for cost, latency, or compatibility reasons.
   282→
   283→Example catalog (keep this updated as new models release):
   284→
   285→```

   292→    ModelInfo(id="claude-sonnet-4-5",             provider="anthropic", display_name="Claude Sonnet 4.5", context_window=200000, supports_tools=true, supports_vision=true, supports_reasoning=true),
   293→
   294→    -- ==========================================================
   295→    -- OpenAI -- prefer GPT-5.2 series for top quality
   296→    -- ==========================================================
   297→
   298→    ModelInfo(id="gpt-5.2",                       provider="openai",    display_name="GPT-5.2",           context_window=1047576, supports_tools=true, supports_vision=true, supports_reasoning=true),
   299→    ModelInfo(id="gpt-5.2-mini",                  provider="openai",    display_name="GPT-5.2 Mini",      context_window=1047576, supports_tools=true, supports_vision=true, supports_reasoning=true),
   300→    ModelInfo(id="gpt-5.2-codex",                 provider="openai",    display_name="GPT-5.2 Codex",     context_window=1047576, supports_tools=true, supports_vision=true, supports_reasoning=true),

   308→]
   309→```
   310→
   311→**Lookup functions:**
   312→
   313→```
   314→get_model_info(model_id: String) -> ModelInfo | None
   315→    -- Returns the catalog entry for a model, or None if unknown.
   316→
   317→list_models(provider: String | None) -> List<ModelInfo>
   318→    -- Returns all known models, optionally filtered by provider.
   319→
   320→get_latest_model(provider: String, capability: String | None) -> ModelInfo | None
   321→    -- Returns the newest/best model for a provider, optionally filtered by capability
   322→    -- (e.g., "reasoning", "vision", "tools"). Useful for coding agents that want
   323→    -- to always use the latest available model.
   324→```
   325→
   326→**Why a catalog matters for coding agents:** When an AI coding agent builds on top of this SDK, it needs to select models by capability (e.g., "pick a model that supports vision" or "pick the cheapest model that supports tools"). Without a catalog, the agent must hallucinate model identifiers from its training data, which go stale as providers release new models. The catalog gives the agent a reliable, up-to-date source of truth.
   327→
   328→The catalog should be shipped as a data file (JSON or similar) that can be updated independently of the library code. Consider auto-generating it from provider documentation or APIs. **When in doubt, prefer the latest models** -- they are generally more capable, and the SDK should make it easy to stay current.

   330→### 2.10 Prompt Caching (Critical for Cost)
   331→
   332→Prompt caching allows providers to reuse computation from previous requests when the prefix of the conversation is unchanged. For agentic workloads where the system prompt and conversation history are identical across many turns, caching can reduce input token costs by 50-90%. The unified SDK MUST support caching for each provider.
   333→
   334→| Provider  | Caching Behavior                                                      | SDK Action Required |
   335→|-----------|-----------------------------------------------------------------------|---------------------|
   336→| OpenAI    | Automatic -- the Responses API caches shared prefixes server-side     | None. Use the Responses API and report `cache_read_tokens` from usage. |
   337→| Gemini    | Automatic -- prefix caching for repeated content, plus explicit `cachedContent` API for long contexts | None for automatic. Expose explicit caching via `provider_options`. |
   338→| Anthropic | **Not automatic.** Requires explicit `cache_control` annotations on content blocks. | The Anthropic adapter must inject `cache_control` breakpoints automatically for agentic workloads. |
   339→
   340→Anthropic is the only provider where the SDK must do extra work. Without cache_control annotations, every turn re-processes the entire system prompt and conversation history at full price. With proper caching, cached input tokens cost 90% less. This is the single highest-ROI optimization for agentic workloads.
   341→
   342→All three providers report cache statistics. The SDK must map these to `Usage.cache_read_tokens` and `Usage.cache_write_tokens` so callers can verify caching is working.

   346→## 3. Data Model
   347→
   348→This section defines all types used by the library. The notation uses a language-neutral struct/record style. Field types use these conventions:
   349→
   350→- `String` -- text
   351→- `Integer` -- whole number
   352→- `Float` -- decimal number
   353→- `Boolean` -- true/false
   354→- `Bytes` -- raw binary data
   355→- `Dict` -- key-value map
   356→- `List<T>` -- ordered collection of T
   357→- `T | None` -- optional (nullable) value
   358→- `T | U` -- union / either type
   359→
   360→### 3.1 Message
   361→
   362→The fundamental unit of conversation. A conversation is an ordered `List<Message>`.
   363→
   364→```
   365→RECORD Message:
   366→    role          : Role                  -- who produced this message
   367→    content       : List<ContentPart>     -- the message body (multimodal)
   368→    name          : String | None         -- for tool messages and developer attribution
   369→    tool_call_id  : String | None         -- links a tool-result message to its tool call
   370→```
   371→
   372→#### Convenience Constructors
   373→
   374→For common cases, factory methods create properly structured Message objects:
   375→
   376→```
   377→Message.system("You are a helpful assistant.")
   378→Message.user("What is 2 + 2?")
   379→Message.assistant("The answer is 4.")
   380→Message.tool_result(tool_call_id = "call_123", content = "72F and sunny", is_error = false)
   381→```
   382→
   383→#### Text Accessor
   384→
   385→A convenience property on Message that concatenates text from all text content parts:
   386→
   387→```
   388→message.text -> String
   389→    -- Returns the concatenation of all ContentPart entries where kind == TEXT.
   390→    -- Returns empty string if no text parts exist.
   391→```
   392→
   393→### 3.2 Role
   394→
   395→Five roles cover the semantics of all major providers:
   396→
   397→```
   398→ENUM Role:
   399→    SYSTEM       -- High-level instructions shaping model behavior. Typically first.
   400→    USER         -- Human input. Text, images, audio, documents.
   401→    ASSISTANT    -- Model output. Text, tool calls, thinking blocks.
   402→    TOOL         -- Tool execution results, linked by tool_call_id.
   403→    DEVELOPER    -- Privileged instructions from the application (not the end user).
   404→```
   405→
   406→Provider mapping for roles:
   407→
   408→| SDK Role    | OpenAI               | Anthropic                          | Gemini                    |
   409→|-------------|----------------------|------------------------------------|---------------------------|
   410→| SYSTEM      | `system` role        | Extracted to `system` parameter    | `systemInstruction`       |
   411→| USER        | `user` role          | `user` role                        | `user` role               |
   412→| ASSISTANT   | `assistant` role     | `assistant` role                   | `model` role              |
   413→| TOOL        | `tool` role          | `tool_result` block in user msg    | `functionResponse` in user|
   414→| DEVELOPER   | `developer` role     | Merged with system                 | Merged with system        |
   415→
   416→### 3.3 ContentPart (Tagged Union)
   417→
   418→Each message contains a list of ContentPart objects. Using a list rather than a single string enables multimodal messages (text interleaved with images), structured assistant responses (text interleaved with tool calls and thinking blocks), and tool results that include images.
   419→
   420→ContentPart uses a tagged-union pattern: the `kind` field determines which data field is populated.
   421→
   422→```
   423→RECORD ContentPart:
   424→    kind          : ContentKind | String  -- discriminator tag
   425→    text          : String | None         -- populated when kind == TEXT
   426→    image         : ImageData | None      -- populated when kind == IMAGE
   427→    audio         : AudioData | None      -- populated when kind == AUDIO
   428→    document      : DocumentData | None   -- populated when kind == DOCUMENT
   429→    tool_call     : ToolCallData | None   -- populated when kind == TOOL_CALL
   430→    tool_result   : ToolResultData | None -- populated when kind == TOOL_RESULT
   431→    thinking      : ThinkingData | None   -- populated when kind == THINKING or REDACTED_THINKING
   432→```
   433→
   434→Note: The `kind` field accepts both the enum and arbitrary strings. This allows extension for provider-specific content kinds without modifying the core enum.
   435→
   436→### 3.4 ContentKind
   437→
   438→```
   439→ENUM ContentKind:
   440→    TEXT                -- Plain text. The most common kind.
   441→    IMAGE               -- Image as URL, base64, or file reference.
   442→    AUDIO               -- Audio as URL or raw bytes with media type.
   443→    DOCUMENT            -- Document (PDF, etc.) as URL, base64, or file reference.
   444→    TOOL_CALL           -- A model-initiated tool invocation.
   445→    TOOL_RESULT         -- The result of executing a tool call.
   446→    THINKING            -- Model reasoning/thinking content.
   447→    REDACTED_THINKING   -- Redacted reasoning (Anthropic). Opaque, must round-trip verbatim.
   448→```
   449→
   450→Direction constraints:
   451→
   452→| Kind              | May appear in roles          |
   453→|-------------------|------------------------------|
   454→| TEXT              | SYSTEM, USER, ASSISTANT, DEVELOPER, TOOL |
   455→| IMAGE             | USER (input), ASSISTANT (generated) |

   463→### 3.5 Content Data Structures
   464→
   465→#### ImageData
   466→
   467→```
   468→RECORD ImageData:
   469→    url         : String | None     -- URL pointing to the image
   470→    data        : Bytes | None      -- raw image bytes
   471→    media_type  : String | None     -- MIME type, e.g. "image/png", "image/jpeg"
   472→    detail      : String | None     -- processing fidelity hint: "auto", "low", "high"
   473→```
   474→
   475→Exactly one of `url` or `data` must be provided. The adapter base64-encodes `data` if the provider requires it. `media_type` defaults to `"image/png"` when `data` is provided and no type is specified.
   476→
   477→**Image upload is critical for multimodal capabilities.** Many models (Claude, GPT-4.1, Gemini) accept image inputs for analysis, code screenshot reading, diagram understanding, and more. The SDK must handle image upload correctly across all providers:
   478→
   479→| Concern              | OpenAI                                               | Anthropic                                         | Gemini                                            |
   480→|----------------------|------------------------------------------------------|---------------------------------------------------|---------------------------------------------------|
   481→| URL images           | `image_url.url` field                                | `source.type = "url"` with `url` field            | `fileData.fileUri` field                          |
   482→| Base64 images        | `image_url.url` as data URI (`data:mime;base64,...`) | `source.type = "base64"` with `data` + `media_type` | `inlineData` with `data` + `mimeType`           |
   483→| File path (local)    | Read file, base64-encode, send as data URI           | Read file, base64-encode, send as base64 source   | Read file, base64-encode, send as inlineData     |
   484→| Supported formats    | PNG, JPEG, GIF, WEBP                                | PNG, JPEG, GIF, WEBP                              | PNG, JPEG, GIF, WEBP, HEIC, HEIF                |
   485→| Max image size       | 20MB                                                 | ~5MB per image (base64 encoded)                   | Varies by method                                  |
   486→| Detail/fidelity hint | `detail`: "auto", "low", "high"                     | Not supported (ignore)                            | Not supported (ignore)                            |
   487→
   488→**Convenience: file path support.** The SDK should accept a local file path as a convenience. When `url` looks like a local file path (starts with `/`, `./`, or `~`), the adapter reads the file, infers the MIME type from the extension, base64-encodes the contents, and sends it using the provider's inline data format. This makes it easy for coding agents to send screenshots and diagrams without manual encoding.
